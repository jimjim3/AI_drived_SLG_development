# 第 3 章：設計原則

## 本章學習目標
- 理解「引擎是唯一的真理來源」架構如何透過不可變狀態與嚴格驗證，確保 AI 代理無法篡改遊戲世界。
- 掌握統一代理介面（Agent Interface）的設計，實現 LLM、規則 AI 與人類輸入的無縫替換與 A/B 對照。
- 認識「玩家與電腦條件完全對稱」原則，探討如何透過相同的視野限制與注意力預算維持實驗公平性。
- 分析確定性與可重現性在 AI 遊戲實驗中的核心地位，理解單一種子偽隨機生成器（PRNG）如何支撐科學驗證。
- 學習面向審查的工程實踐，透過自解釋日誌與 Headless 模擬，拒絕黑盒決策並建立可觀測的決策鏈。

## 3.1 引擎是唯一的真理來源

在傳統軟體工程中，「單一事實來源」（Single Source of Truth）是避免狀態不一致的核心原則。在本專案中，這一原則被強化為一個嚴格的架構約束：**引擎是唯一的真理來源**。這意味著遊戲世界的所有狀態遷移、資源結算與事件觸發，必須且只能由遊戲引擎（Game Engine）執行。AI 代理（無論是大型語言模型 LLM 還是規則型 AI）永遠無法直接修改遊戲狀態。

這一原則的技術實現依賴於兩個關鍵機制：**不可變狀態架構**（Immutable State Architecture）與**執行前驗證**（Pre-execution Validation）。

首先，遊戲狀態在 Python 中透過 `dataclass` 定義，並採用凍結（frozen）策略或複製寫入（Copy-on-Write）模式。在 `src/slg/schema.py` 中，`GameState`、`CityState` 與 `OfficerState` 等核心資料結構被設計為不可變或受控變異。當引擎進行結算時，它不會直接在記憶體中修改現有物件的屬性，而是生成一個新的狀態物件。這種設計確保了任何時刻的狀態都是可追溯且一致的，避免了因並行執行或異常中斷導致的「髒數據」。

其次，AI 的決策過程被嚴格限制在「選擇」而非「創造」。引擎透過 `generate_legal_actions` 函式，根據當前城池狀態、武將屬性與資源限制，動態產生一個「合法行動清單」（Legal Action List）。這個清單定義了當下所有可能的操作及其參數範圍（例如：徵兵數量的最小值、最大值與步長）。AI 代理只能從這個清單中挑選一個行動並填入參數。

然而，僅提供清單並不足以保證安全性。AI 可能產生格式錯誤、參數越界或違反前置條件的輸出。因此，引擎在執行任何行動前，會透過 `validate_decision` 函式進行嚴格的二次重驗。此驗證過程檢查行動名稱是否合法、參數型別是否正確、數值是否在允許範圍內，以及資源成本（如金錢、糧食）是否充足。若驗證失敗，該行動將被拒絕，並觸發安全網機制（Safety Net），例如重試或退回規則 AI。

這種架構確保了 AI 永遠無法「作弊」或導致遊戲崩潰。即使 LLM 產生荒謬的指令（如「瞬移軍隊」或「無限徵兵」），引擎也會因為該行動不在合法清單中或參數驗證失敗而拒絕執行。這不僅是安全機制，更是實驗有效性的基礎：它保證了所有被觀察到的遊戲結果，都是基於相同規則集與相同狀態遷移邏輯產生的，而非 AI 的幻覺或錯誤。

## 3.2 Agent 是可替換的決策插件

為了進行嚴謹的科學實驗，必須能夠在控制變量的前提下比較不同決策策略的性能。因此，本系統將 AI 決策層抽象為**可替換的決策插件**（Pluggable Decision Plugin）。這意味著無論底層是複雜的 LLM、簡單的規則引擎，甚至是人類玩家，它們都必須實現統一的代理介面（Agent Interface）。

在 `src/slg/agents/base.py` 中，定義了兩個核心抽象類別：`Agent`（官員層級）與 `FactionAgent`（勢力層級）。`FactionAgent` 的 `decide` 方法接收一個 `FactionView`（包含該勢力可見的遊戲狀態摘要）作為輸入，並回傳一個 `FactionPlan`（包含 `orders`、`chronicle` 與 `next_cast`）作為輸出。這種輸入/輸出契約的標準化，使得系統可以無縫切換不同的實現：

1.  **LLMFactionAgent**：負責將遊戲狀態轉化為 Prompt，呼叫 LLM API，解析 JSON 輸出，並處理錯誤重試。
2.  **RuleBasedAgent**：基於硬編碼的邏輯規則（如兵力對比、資源匱乏程度）做出決策。它提供三種風格（`balanced`、`aggressive`、`turtle`），作為實驗的基準線（Baseline）。
3.  **RandomAgent**：在合法參數空間中隨機抽樣，用於測試系統對隨機輸入的魯棒性。
4.  **HumanAgent**：預留給人類玩家輸入的介面，確保人類與 AI 在相同的資訊條件下操作。

這種設計帶來了兩方面的重要優勢。第一，它支持 A/B 對照實驗。研究者可以固定遊戲種子與初始狀態，分別使用 LLM 與規則 AI 進行對局，比較勝率、資源消耗與戰略穩定性。第二，它提供了容錯機制。當 LLM 呼叫失敗、超時或產生非法輸出時，系統可以自動退回 `RuleBasedAgent`，確保遊戲不會中斷。這種「優雅降級」（Graceful Degradation）機制對於長時間的大規模模擬至關重要。

此外，插件化設計也促进了模組化開發。不同的 LLM 後端（如 OpenAI API、本機 Ollama、或離線 DemoCompleter）可以透過 `backends.py` 中的 `Completer` 介面接入，無需修改核心代理邏輯。這使得系統可以靈活適配不同規模與能力的模型，並便於未來擴展新的決策策略。

## 3.3 條件完全對稱性

在 AI 與人類或 AI 之間的對戰中，公平性是實驗可信度的基石。本專案嚴格遵循**玩家與電腦條件完全對稱**的原則。這意味著，無論決策者是人類還是 AI，他們看到的資訊、擁有的操作權限與受到的限制必須完全一致。

具體而言，對稱性體現在以下幾個方面：

1.  **視野限制（Fog of War）**：所有勢力（包括玩家與 AI）都只能看到己方城池與相鄰的敵方前線城池（`frontier`）。非相鄰的敵方城池狀態完全隱蔽。這消除了「全知視角」（God View）的作弊可能，迫使決策者必須基於不完整資訊進行推理。引擎透過 `build_faction_view` 函式為每個勢力生成獨立的視野視圖，確保資訊隔離。
2.  **注意力預算（Attention Budget）**：為了模擬人類或 AI 的認知限制，系統引入了「出場名單」（Cast List）機制。每個勢力每回合只能詳細關注有限數量的武將（上限 `CAST_LIMIT = 6`）。未出現在名單中的武將，其詳細狀態不會進入 Prompt 或玩家界面，而是由規則 AI 自動委任代理（Delegation）執行基礎行動。這一機制對所有勢力一視同仁，確保了 Token 消耗與決策顆粒度的對稱。
3.  **操作介面統一**：玩家的操作（透過 UI 或 API）與 AI 的輸出（`orders` + `next_cast`）在邏輯上是等價的。玩家不能執行 AI 無法執行的行動，反之亦然。所有行動都必須經過引擎的 `validate_decision` 驗證，確保規則應用的一致性。

這種對稱性設計不僅是遊戲平衡的需要，更是科學實驗的方法論要求。如果玩家擁有 AI 沒有的優勢（如即時資訊或無限注意力），實驗結果將無法反映 AI 的真實決策能力。通過強制對稱，研究者可以確保觀察到的性能差異源於決策策略本身，而非資訊不對稱或規則偏袒。

## 3.4 確定性與可重現性

在涉及隨機性與非確定性模型（如 LLM）的系統中，**確定性**（Determinism）與**可重現性**（Reproducibility）是驗證假說與調試錯誤的生命線。本系統採用**單一種子偽隨機生成器**（Single-Seed PRNG）策略，確保任意對局在相同輸入下 100% 逐位元重現。

所有遊戲中的隨機事件——包括行動順序洗牌、戰鬥結果波動、資源收入擾動（U(0.8, 1.2)）與俘虜轉投判定——都由一個中央管理的 `random.Random` 實例驅動。該實例在遊戲初始化時以指定的種子（Seed）初始化。這意味著，只要種子相同、初始狀態相同、且 AI 代理的決策序列相同，遊戲的演進路徑將完全一致。

為了實現這一目標，系統引入了 `TurnLog` 機制。`TurnLog` 記錄了每個回合中每個勢力的實際執行決策（`executed`）、引擎產生的隨機數序列以及關鍵狀態快照。`src/slg/sim/replay.py` 中的 `replay` 函式可以讀取這些日誌，並透過 `ReplayFactionAgent` 強制代理在每個回合做出與原始對局相同的決策，從而精確還原遊戲狀態。

這種可重現性對於以下場景至關重要：
1.  **除錯**：當出現異常行為時，開發者可以透過日誌重播問題場景，逐步追蹤狀態遷移，定位錯誤根源。
2.  **實驗驗證**：研究者可以多次運行相同種子的對局，比較不同 AI 配置的表現，排除隨機噪聲的干擾。
3.  **回歸測試**：在修改引擎規則或代理邏輯後，可以透過重播歷史對局，驗證修改是否導致了非預期的行為變化。

值得注意的是，LLM 本身的輸出可能具有非確定性（Temperature > 0）。為了應對這一挑戰，實驗設計中通常會固定 LLM 的 Temperature 為 0，或在日誌中記錄 LLM 的原始輸出，以便在重播時使用相同的輸入與輸出對。這確保了即使模型本身具有隨機性，整個系統的行為在給定日誌下仍是可重現的。

## 3.5 面向審查的工程實踐

在 AI 驅動的系統中，決策過程往往被視為「黑盒」。然而，對於科學實驗與工程維護而言，黑盒是不可接受的。本專案採取**面向審查**（Audit-Oriented）的工程實踐，確保每一條決策與結算皆具備自解釋日誌（Self-Explanatory Logs）。

這種實踐體現在以下幾個層面：

1.  **決策透明化**：`FactionPlan` 中包含 `memo`（奏摺）欄位，要求 LLM 在發出指令時提供簡短的理由說明。雖然這不強制約束 LLM 的邏輯，但它為人類審查者提供了理解 AI 意圖的線索。此外，`chronicle`（紀事）欄位記錄了 AI 對當前局勢的敘事性描述，有助於分析 AI 的世界模型是否與實際狀態一致。
2.  **拒絕原因反饋**：當引擎拒絕 AI 的某個指令時，拒絕原因（如「資金不足」、「參數越界」）會被記錄在日誌中，並在下回合的 `FactionView` 中反饋給 AI。這不僅幫助 AI 學習修正錯誤，也為研究者提供了 AI 決策失敗模式分析。
3.  **Headless 模擬與統計**：`src/slg/sim/headless.py` 提供了無畫面（Headless）的對局模擬功能，可以大量自動運行對局並收集統計數據（如勝率、平均存活回合、Token 消耗）。這些數據是評估 AI 性能與驗證平衡性的基礎。
4.  **完整狀態追蹤**：`TurnLog` 不僅記錄決策，還記錄每個回合的關鍵狀態指標（如各城池兵力、資源、武將忠誠度）。這使得研究者可以事後分析特定事件（如城市陷落）的前因後果，而不需要實時監控。

透過這些實踐，系統拒絕了「AI 說了算」的黑盒模式，轉而建立了一個可觀測、可分析、可驗證的決策環境。這不僅提升了軟體的可維護性，也增強了實驗結果的可信度與可解釋性。

## 本章重點
- **引擎是唯一的真理來源**：透過不可變狀態與執行前驗證，確保 AI 無法直接篡改世界狀態，所有狀態遷移均由引擎控制。
- **可替換的決策插件**：統一的 `Agent` 介面允許 LLM、規則 AI 與人類無縫切換，支持 A/B 對照與自動容錯降級。
- **條件完全對稱**：玩家與電腦適用相同的視野限制（戰爭迷霧）與注意力預算（出場名單），確保實驗公平性。
- **確定性與可重現性**：單一種子 PRNG 與 `TurnLog` 重播機制，保證相同輸入下 100% 逐位元重現，支撐科學驗證。
- **面向審查的工程實踐**：透過自解釋日誌、拒絕原因反饋與 Headless 統計，拒絕黑盒決策，提升系統可觀測性。
- **安全網機制**：AI 決策異常時自動重試或退回規則 AI，確保遊戲流程不中斷且 `valid == decisions`。
- **模組化架構**：引擎、代理與模擬層分離，便於獨立開發、測試與擴展。

## 習題
1.  **狀態一致性驗證**：假設在某一回合中，LLM 產生了一個參數合法的 `recruit` 行動，但引擎在 `validate_decision` 階段拒絕了該行動。請列出至少三種可能的拒絕原因，並說明系統將如何處理此異常（重試或降級）。
2.  **對稱性影響分析**：如果移除「出場名單」限制，允許 AI 每回合詳細關注所有武將，這將對 LLM 的 Token 消耗與決策質量產生什麼影響？請結合 DESIGN.md 中的 Token 預算估算進行討論。
3.  **重現性測試設計**：設計一個單元測試用例，驗證 `replay` 模組能否在給定相同 `TurnLog` 與種子的情況下，完全還原原始對局的最終狀態。請說明測試中需要比對的關鍵狀態變數。
4.  **代理介面擴展**：若要將一個基於強化學習（RL）的代理接入本系統，需要實現 `FactionAgent` 介面的哪些方法？RL 代理的「觀察」（Observation）與「動作」（Action）空間應如何映射到 `FactionView` 與 `FactionPlan`？
5.  **黑盒審查案例**：在實驗中發現某 LLM 勢力在資源匱乏時頻繁選擇 `rest` 而非 `develop`。請設計一個日誌分析流程，利用 `memo` 與 `chronicle` 欄位，判斷這是 AI 的戰略選擇還是模型對規則的誤解。
