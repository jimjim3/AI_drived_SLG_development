# 第 5 章：引擎實作與安全網

## 本章學習目標
- 理解 `generate_legal_actions` 如何作為唯一真理來源，動態生成精確的合法動作空間，並杜絕非法參數組合。
- 掌握 `validate_decision` 與 `resolve_decision` 的兩段式驗證機制，確保在並行或狀態變動下決策的有效性與結算的安全性。
- 分析引擎的安全網設計，特別是當 LLM 輸出無效指令時，如何透過規則 AI 兜底與 `rest` 保底，嚴格維持 `valid == decisions` 的不變量。
- 學習 `TurnLog` 的結構與記錄邏輯，理解其如何完整捕捉每回合的動作、決策來源與結算事件。
- 探討 `ReplayDelegateAgent` 與確定性重播系統，了解如何依日誌 100% 重構歷史狀態，杜絕模擬發散。

## 5.1 合法行動枚舉：generate_legal_actions 產生精確動作空間

在分層 AI 決策架構中，引擎（Engine）必須是唯一的真理來源（Single Source of Truth）。LLM 或任何代理（Agent）不具備直接修改遊戲狀態的權力，其所有行動必須嚴格限制在引擎當前允許的範圍內。`legal_actions.py` 模組中的 `generate_legal_actions` 函式承擔了這一核心職責。它接收當前的 `GameState` 與特定的 `OfficerState`，並回傳一個 `LegalAction` 物件的列表。這個列表不僅定義了「可以做什麼」，更精確地定義了「參數的合法範圍」。

與傳統遊戲引擎僅提供動作名稱不同，本系統的 `LegalAction` 結構包含了 `params` 欄位，該欄位使用 `ParamSpec` 來描述每個參數的約束條件。例如，對於 `recruit`（徵兵）動作，`ParamSpec` 會計算出 `min`、`max` 與 `step`。具體而言，最大徵兵數量受限于 `MAX_RECRUIT` 與城池金錢除以 `GOLD_PER_TROOP` 的商，並向下取整至 `RECRUIT_STEP` 的倍數。若此最大值小於 `MIN_RECRUIT`，則該動作根本不會出現在列表中。這種設計從源頭上杜絕了 LLM 嘗試執行「徵兵 0 人」或「徵兵非整數倍數」等無意義或非法操作的可能性。

同樣地，`siege`（攻城）動作的參數生成邏輯更為複雜。它首先檢查是否存在相鄰的敵方城市，並計算可動用的最大兵力。此計算需扣除 `SIEGE_MIN_GARRISON`（留守最低兵力），確保城市不會因空虛而立即淪陷。可動用兵力同樣需符合 `SIEGE_TROOP_STEP` 的步長限制。只有當計算出的最大兵力大於等於 `MIN_SIEGE_TROOPS` 時，攻城動作才會被加入合法清單。這種精細的參數約束使得代理在生成決策時，只需在離散的格點或連續的區間內選擇，大幅降低了生成非法輸入的機率。

此外，`develop_agri`、`develop_commerce` 與 `develop_defense` 等開發動作，其合法性取決於城池金錢是否大於等於 `DEVELOP_COST`。值得注意的是，這些動作的 `note` 欄位會動態計算預期收益，該收益由 `develop_gain` 函式根據基礎值與武將的 `politics`（政治力）算出。這意味著引擎不僅提供動作選項，還提供了基於當前狀態的即時預覽，幫助 LLM 做出更明智的決策。最後，`rest`（休息）動作被無條件地追加到列表末尾，標註為 "always available"。這不僅是一個備選動作，更是後續安全網機制中「保底執行」的基礎，確保在任何極端情況下，代理總有一個合法的動作可以執行。

## 5.2 嚴格二重驗證：validate_decision 確保狀態未於並行中失效

儘管代理僅從 `generate_legal_actions` 提供的列表中選擇動作，但引擎仍必須在執行前進行嚴格的二重驗證。這是因為遊戲狀態可能在代理生成決策後、引擎處理決策前發生變化（例如在勢力層級決策中，同一回合內其他武將的行動可能改變了城池資源），或者代理本身生成了格式錯誤的數據。`validation.py` 模組中的 `validate_decision` 函式承擔了這一安全檢查任務。它接收 `state`、`officer` 與 `decision` 三個參數，回傳一個包含布林值與錯誤訊息的元組。

驗證過程首先檢查 `officer_id` 是否匹配以及武將是否存活。接著，它檢查動作名稱是否屬於 `KNOWN_ACTIONS` 集合。隨後，引擎會重新呼叫 `generate_legal_actions` 以獲取當前狀態下的合法動作集合，並檢查決策中的動作是否在其中。這一步驟確保了動作的「時效性」，即該動作在當前瞬間仍然是合法的。

更關鍵的是參數驗證。`validate_decision` 會遍歷 `LegalAction` 中定義的 `params` 規範，並與決策中提供的 `params` 進行比對。它首先檢查是否缺少必要的參數，或是否包含了未定義的參數。對於每個存在的參數，若其為離散型（`is_discrete()` 為真），則檢查值是否在 `choices` 元組中；若為連續型，則檢查值是否在 `[min, max]` 區間內，且若定義了 `step`，則檢查 `(value - min) % step` 是否為零。這種嚴格的參數校驗防止了 LLM 可能產生的「近似值」錯誤，例如將 100 人徵兵誤寫為 101 人。

最後，驗證函式會計算動作的成本（`_action_cost`），並檢查城池金錢是否足夠。對於 `recruit` 動作，成本為 `troops * GOLD_PER_TROOP`；對於開發動作，成本為固定的 `DEVELOP_COST`；其他動作成本為 0。若金錢不足，驗證將失敗並回傳具體的短缺金額。這種多層次的驗證機制，使得 `validate_decision` 成為一道堅固的防火牆，確保只有完全符合引擎規則的決策才能進入結算階段。

## 5.3 兜底安全網：確保 valid == decisions 的關鍵不變量

在 `game.py` 的 `decide` 方法中，實現了一套多層次的兜底安全網（Safety Net）。其核心目標是維護一個關鍵的不變量：`stats["valid"] == stats["decisions"]`。這意味著，每當引擎為一個武將生成一個決策計數（`decisions` 增加 1），最終必須有一個有效的決策被接受並執行（`valid` 增加 1）。若此不變量被破壞，遊戲狀態將陷入不一致，導致模擬崩潰。

安全網的第一層是主代理（Primary Agent）的重試機制。在 `decide` 方法中，系統會嘗試讓主代理（可能是 LLM 或規則 AI）做出決策。此過程最多進行兩次嘗試。在每次嘗試中，若代理拋出異常（Exception），系統會捕獲該異常。特別地，若代理名稱為 "replay_delegate"，異常會被重新拋出，因為重播模式要求嚴格的一致性，不允許靜默失敗。對於其他代理，系統會增加 `stats["rejected"]` 計數並繼續下一次嘗試。若代理成功回傳決策，系統會呼叫 `validate_decision` 進行驗證。若驗證通過，`stats["valid"]` 增加，並回傳該決策。若驗證失敗，同樣增加 `rejected` 計數並進入下一次嘗試。

若主代理的兩次嘗試均失敗（無論是異常還是驗證失敗），系統將進入第二層兜底：規則 AI（Rule-Based Agent）。系統會增加 `stats["fallbacks"]` 計數，並呼叫 `self._fallback.decide`（預設為 `RuleBasedAgent`）生成一個新決策。此決策同樣會經過 `validate_decision` 驗證。由於規則 AI 的邏輯是基於引擎規則編寫的，其生成的決策理論上應始終合法。若驗證通過，`stats["valid"]` 增加，並回傳該規則決策，標記 `fallback` 為 `True`。

最後，若連規則 AI 的決策都因某種不可預見的原因（如狀態在極端情況下變得更為嚴格）而驗證失敗，系統將進入第三層兜底：硬編碼的 `rest` 動作。系統直接構造一個 `AgentDecision(officer.officer_id, "rest")`，並增加 `stats["valid"]` 計數，回傳此決策，標記來源為 "safety_net"。由於 `rest` 動作在 `generate_legal_actions` 中被標註為 "always available" 且成本為 0，它在任何遊戲狀態下都是合法的。

這套三層安全網設計，確保了無論 LLM 輸出多麼混亂、異常，或規則 AI 出現極端邊界情況，引擎都能保證產出一個合法的決策。這不僅保護了遊戲的穩定性，也為後續的日誌記錄與重播提供了數據完整性保證。`valid == decisions` 的不變量是遊戲永不崩潰的基石，它將不確定的 AI 行為封裝在確定的引擎規則之內。

## 5.4 完整對局日誌 TurnLog：記錄每回合所有動作、決策來源與結算事件

為了實現可重現性與事後分析，引擎必須完整記錄遊戲過程中的每一個決策與狀態變化。`TurnLog` 與 `LogEntry` 結構承擔了這一記錄職責。在 `headless.py` 的 `run_headless` 函式中，遊戲結束後，系統會將 `game.log_entries` 與 `game.faction_logs` 彙整成一個 `TurnLog` 物件，並包含在 `GameResult` 中回傳。

`LogEntry` 是記錄單一武將單一決策的最小單位。它包含以下關鍵欄位：
- `turn`：當前回合數。
- `officer_id` 與 `faction_id`：決策者與所屬勢力。
- `agent_name`：做出決策的代理名稱（如 "llm", "rule_based", "safety_net"）。
- `legal_count`：該回合該武將的合法動作數量，用於分析動作空間的大小。
- `action` 與 `params`：實際執行的動作名稱與參數。
- `valid` 與 `fallback`：標記該決策是否有效，以及是否使用了兜底機制。
- `event`：結算後產生的 `ResolutionEvent`，包含動作執行後的具體效果（如金錢變化、兵力變化、戰鬥結果等）。
- `source`：決策來源，區分為 "agent"（主代理）、"order"（勢力層級指令）、"delegate"（委任代理）或 "disobey"（抗旨）。

在勢力層級決策（`FactionAgent`）的流程中，`FactionTurnLog` 提供了更高層次的記錄。它記錄了該勢力在該回合的 `executed`（實際執行的決策元組）、`chronicle`（LLM 生成的紀事文本）、`next_cast`（下回合點名出場名單）、`rejected`（被引擎拒絕的指令清單）、`delegated`（被委任代理處理的武將 ID）以及 `plan_failed`（規劃是否失敗）。

這種分層記錄機制使得研究者可以精確追溯每個決策的來源與結果。例如，可以統計 LLM 生成的指令被拒絕的比例，分析拒絕原因（如金錢不足、參數越界），從而優化 Prompt 工程或調整 LLM 的參數。同時，`ResolutionEvent` 的記錄使得結算過程透明化，便於驗證戰鬥公式與資源計算的正確性。`TurnLog` 不僅是調試工具，更是後續實驗分析與確定性重播的數據基礎。

## 5.5 確定性重播：ReplayDelegateAgent 依日誌 100% 重構歷史狀態

確定性重播（Deterministic Replay）是驗證模擬系統正確性與可重現性的關鍵技術。`replay.py` 模組實現了這一功能，允許系統依據先前生成的 `TurnLog` 重新執行遊戲，並驗證其結果是否與原始執行完全一致。重播的核心在於使用特殊的代理類別：`ReplayFactionAgent` 與 `ReplayDelegateAgent`。

`ReplayFactionAgent` 繼承自 `FactionAgent`，其 `decide` 方法不進行任何邏輯計算，而是直接從預載入的日誌記錄中查表回傳決策。它在初始化時，將 `FactionTurnLog` 中的 `executed` 決策按 `(turn, faction_id)` 建立索引。當引擎呼叫其 `decide` 時，它根據當前的 `turn` 與 `faction_id` 查表並回傳對應的 `FactionPlan`。若查表失敗，則拋出 `AgentError`，確保重播過程的嚴格性。

`ReplayDelegateAgent` 繼承自 `Agent`，用於處理委任代理的決策。它同樣從日誌中查表，但索引鍵為 `(turn, officer_id)`。這確保了當引擎在勢力層級決策後，對未點名武將進行委任代理時，重播系統能回傳與原始執行完全相同的決策。

`replay` 函式是重播的入口點。它接收一個 `TurnLog` 物件，並執行以下步驟：
1. 根據日誌中的 `scenario` 重建初始狀態 `GameState`。
2. 使用日誌中的 `seed` 初始化隨機數生成器 `rng`。這是確定性重播的關鍵，因為所有隨機事件（如收入擾動、戰鬥結果、抗旨擲骰）都依賴於此 RNG 的狀態序列。
3. 為日誌中出現的所有勢力創建 `ReplayFactionAgent` 實例，並創建一個 `ReplayDelegateAgent` 實例。
4. 創建 `Game` 實例，並執行 `run(log.turns)`。
5. 回傳 `GameResult`，包含最終狀態、統計數據、事件列表與勝負結果。

由於 `ReplayFactionAgent` 與 `ReplayDelegateAgent` 嚴格遵循日誌中的決策，且 RNG 的種子相同，遊戲狀態的遷移應與原始執行完全一致。這使得開發者可以通過比較重播結果與原始結果的 `stats`、`events` 與 `final_state`，來驗證引擎的確定性。若出現任何差異，則表明系統中存在非確定性因素（如未控制的隨機性、並行競爭條件或狀態變更順序錯誤）。`ReplayDelegateAgent` 在此過程中扮演了關鍵角色，它確保了委任代理的決策也被精確重現，從而實現了對整個遊戲過程 100% 的歷史狀態重構，杜絕了模擬發散。

## 本章重點
- `generate_legal_actions` 是引擎的唯一真理來源，它根據當前狀態動態生成包含精確參數約束（min, max, step, choices）的合法動作列表，從源頭限制代理的行動空間。
- `validate_decision` 執行嚴格的二重驗證，包括動作名稱、參數範圍、步長對齊、金錢成本與前置條件檢查，確保決策在當前狀態下仍然有效。
- 安全網機制通過「主代理重試 → 規則 AI 兜底 → rest 保底」的三層防禦，嚴格維持 `valid == decisions` 的不變量，確保遊戲在面對 LLM 異常或非法輸出時永不崩潰。
- `TurnLog` 與 `LogEntry` 提供了完整的對局記錄，涵蓋每回合的動作、參數、決策來源（agent/order/delegate/disobey）與結算事件，支持深度的事後分析與調試。
- `ReplayDelegateAgent` 與 `ReplayFactionAgent` 實現了確定性重播，通過查表回傳歷史決策並配合固定種子的 RNG，能 100% 重構歷史狀態，驗證模擬系統的確定性與正確性。

## 習題
1. 假設某城池金錢為 500，`DEVELOP_COST` 為 200，`GOLD_PER_TROOP` 為 10，`MIN_RECRUIT` 為 100，`RECRUIT_STEP` 為 50。請計算 `generate_legal_actions` 中 `recruit` 動作的 `max` 參數值，並說明若金錢為 450 時該動作是否會出現。
2. 在 `validate_decision` 中，若 LLM 輸出的 `recruit` 動作參數 `troops` 為 150，但 `ParamSpec` 定義的 `step` 為 100，`min` 為 100。請說明驗證函式將回傳什麼錯誤訊息，並解釋其判斷邏輯。
3. 若主代理連續兩次拋出 `Exception`，規則 AI 回傳的決策因金錢不足被 `validate_decision` 拒絕，請描述引擎最終會執行哪個動作，並說明 `stats` 中 `rejected`、`fallbacks` 與 `valid` 計數的變化。
4. `ReplayDelegateAgent` 的索引鍵為 `(turn, officer_id)`。若在同一回合中，同一武將先被勢力層級指令點名（source="order"），後又被委任代理處理（source="delegate"），這在邏輯上是否可能？請根據 `game.py` 的 `step` 方法邏輯說明原因。
5. 為什麼 `rest` 動作在 `generate_legal_actions` 中被標註為 "always available" 且成本為 0？這對於安全網的第三層兜底機制有何重要意義？
