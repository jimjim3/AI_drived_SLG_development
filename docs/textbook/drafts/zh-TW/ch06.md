# 第 6 章：LLM 代理

## 本章學習目標
1. 理解 `SYSTEM_PROMPT` 如何透過嚴格的輸出契約與短碼格式規範，引導大型語言模型（LLM）產生結構化決策。
2. 掌握 `parse_plan` 函式中 `raw_decode` 的魯棒性設計，解析從夾帶雜訊之生成文本中精確提取第一個合法 JSON 物件。
3. 熟悉多後端 `Completer` 架構，包括 `OpenAIChatCompleter`、離線 `DemoCompleter` 與外部命令後端的實作差異。
4. 探討思考標記與延遲抑制機制，理解關閉 `enable_thinking` 如何縮短推論時間並杜絕長鏈推理超時。
5. 分析異常隔離與斷路器模式，說明 `CircuitBreakerCompleter` 如何防範連續 API 故障，以及 `ConfigError` 如何快速暴露設定缺陷。

## 6.1 系統提示詞工程：SYSTEM_PROMPT 規範嚴格輸出契約與短碼格式

在將 LLM 整合進策略遊戲引擎時，首要挑戰在於將非結構化的自然語言輸出轉化為引擎可執行的結構化指令。`llm_agent.py` 中的 `SYSTEM_PROMPT` 承擔了定義這一「輸出契約」的核心角色。該提示詞並非單純的角色扮演設定，而是一份精確的技術規格說明書，它明確界定了 LLM 作為「勢力謀主」的職責邊界與行為約束。提示詞開頭即宣告「每位出場武將每回合至多一個行動」，並強調「行動只能取自該武將 legal 清單，參數須在範圍內」。這種嚴格的約束旨在防止 LLM 產生幻覺（Hallucination）或越權操作，確保生成的指令符合遊戲世界的物理與規則限制。

為了降低 LLM 在參數生成上的錯誤率，`SYSTEM_PROMPT` 採用了「短碼格式」（Short-code Format）與明確的範例引導。提示詞中詳細列出了 `params` 的鍵名必須與 `legal` 清單中的鍵名完全相同，並特別指出「值為單一字串或數字，不可為陣列」。針對常見的格式錯誤，如將 `to` 參數傳入長度為 1 的陣列 `['wancheng']`，提示詞中透過「legal 清單中若標示 to=[a,b]，表示 to 只能取 a 或 b 其中一個，不可為陣列」的明確規定進行預防。此外，提示詞提供了具體的 JSON 範例，如 `{"officer":"<officer_id>","action":"move","params":{"to":"<city_id>"},"memo":"…"}`，這些範例不僅展示了結構，更透過佔位符 `<officer_id>` 與 `<city_id>` 暗示了資料型別，幫助模型理解參數的語意。

`SYSTEM_PROMPT` 的另一個關鍵功能是戰略引導。它不僅關注指令的格式，還嵌入了遊戲策略的邏輯。例如，提示詞中明確告知 LLM 在出征前需比較 `frontier` 中敵城的 `troops` 與 `defense`，並參考 `cast` 中的 `siege_odds`。透過定義「勝算比 = 攻方戰力 ÷ 守方戰力（不含隨機）」，並警告「實戰有約 ±15% 的隨機，比值低於 1.3 的出征很可能失敗並損失大量兵力」，提示詞將抽象的遊戲機制轉化為具體的決策依據。這種設計使得 LLM 不僅是語法生成器，更是具備一定策略判斷能力的代理。最後，提示詞以「輸出只能是一個 JSON 物件」結尾，並禁止輸出 JSON 以外的文字，這為後續的解析器提供了明確的輸入預期，減少了因格式雜訊導致的解析失敗。

## 6.2 容錯 JSON 解析：parse_plan 與 raw_decode 從夾帶雜訊之生成文本中精確提取第一個合法 JSON 物件

儘管 `SYSTEM_PROMPT` 嚴格要求輸出純 JSON，實際的 LLM 生成結果往往夾帶 Markdown 代碼塊標記（如 ```json）、開頭或結尾的解釋性文字，甚至是多個 JSON 物件。`parse_plan` 函式正是為了處理這些非理想輸入而設計的容錯解析器。其核心策略是「從夾帶雜訊之生成文本中精確提取第一個合法 JSON 物件」。函式首先檢查輸入文本中是否包含 ``` 標記，若存在，則將搜索起點移至該標記之後，以跳過可能的代碼塊語法。接著，它利用 `json.JSONDecoder` 的 `raw_decode` 方法，從文本中第一個 `{` 或 `[` 開始嘗試解析。

`raw_decode` 的魯棒性設計在於它不要求整個輸入字符串都是合法的 JSON，而是從指定索引開始解析，直到遇到合法的 JSON 結尾為止。這意味著，如果 LLM 在輸出完整 JSON 物件後，又在尾端多寫了第二個物件或補充文字（即 EVALUATION.md 中提到的 `Extra data` 問題），`raw_decode` 會成功解析第一個物件並忽略其後的內容。在 `parse_plan` 的實作中，程式碼會比較 `{` 與 `[` 的位置，若陣列起始位置早於物件起始位置，則先嘗試解析陣列，但隨後會檢查頂層是否為 `dict`，因為 `FactionPlan` 的結構要求頂層必須是包含 `orders`、`chronicle` 與 `next_cast` 的字典。若解析出的頂層不是字典，則拋出 `PlanParseError`。

解析過程還包含了對參數格式的歸一化（Normalization）。LLM 可能使用非標準的鍵名，如 `target` 或 `destination` 代替 `to`，或使用 `soldiers` 代替 `troops`。`parse_plan` 定義了 `TO_ALIASES` 與 `TROOPS_ALIASES` 元組，並在解析 `params` 時進行別名映射。此外，若 LLM 將單值參數包裹在長度為 1 的陣列中（如 `["wancheng"]`），解析器會自動提取陣列中的第一個元素並將其轉為純值。這些歸一化步驟不僅提高了指令的接受率，也記錄了 `normalized_params` 統計數據，用於後續的效能分析。透過這種多層次的容錯與歸一化機制，`parse_plan` 將 LLM 的「模糊輸出」轉化為引擎可精確執行的「確定性指令」，顯著降低了因格式問題導致的重試次數與 API 成本。

## 6.3 多後端 Completer 架構：OpenAIChatCompleter、離線 DemoCompleter 與外部命令後端

為了實現 LLM 代理與具體模型服務的解耦，系統定義了 `Completer` 型別，即一個接收 `system` 與 `user` 提示詞並返回字串回應的可呼叫物件。`backends.py` 提供了多種實作，以適應不同的開發、測試與部署場景。其中，`OpenAIChatCompleter` 是生產環境的主要後端，它透過標準庫 `urllib` 呼叫 OpenAI 相容的 `/chat/completions` REST API。該實作不僅處理了基本的 HTTP 請求與回應解析，還包含了嚴格的環境變數驗證。若 `api_key_env` 指定的環境變數值包含非 ASCII 字元或空白字元，會立即拋出 `ConfigError`，防止因配置錯誤（如貼上佔位文字）而導致後續的無效 API 呼叫。

`DemoCompleter` 則是一個離線示範後端，專為無網路環境或快速原型驗證而設計。它不依賴任何外部 API，而是直接解析 `user` 提示詞中的 `狀態：` 部分，提取遊戲狀態 JSON，並根據武將的 `legal` 清單簡單地選擇第一個非 `rest` 行動作為輸出。雖然 `DemoCompleter` 的策略極為簡單（僅選擇第一個合法行動），但它能產生符合格式要求的 JSON 回應，使得開發者可以在本地環境中測試 `parse_plan` 與引擎的互動邏輯，而無需消耗 API 額度。此外，`CommandCompleter` 提供了執行外部命令列程式的能力，透過標準輸入或臨時檔案傳遞提示詞，這為整合本機部署的 LLM 服務（如 llama-server）或自訂腳本提供了靈活性。

這種多後端架構的設計優勢在於其可替換性。`LLMFactionAgent` 僅依賴 `Completer` 介面，因此可以在不修改代理邏輯的情況下，將後端從 `OpenAIChatCompleter` 切換為 `DemoCompleter` 或 `CommandCompleter`。在 `OpenAIChatCompleter` 中，`extra_body` 參數允許注入額外的 API 參數，例如在 Qwen 實驗中使用的 `{"chat_template_kwargs":{"enable_thinking":false}}`。這種靈活性使得系統能夠適應不同模型提供商的特定需求，同時保持核心代理邏輯的穩定性。透過抽象化後端實現，系統不僅提高了可維護性，也為未來的模型擴展與效能調優奠定了基礎。

## 6.4 思考標記與延遲抑制：關閉 enable_thinking 縮短推論時間，杜絕長鏈推理超時

在部署本機或雲端 LLM 時，推論延遲（Inference Latency）是影響遊戲回合週期與玩家體驗的關鍵因素。部分先進的 LLM（如 Qwen 系列）支援「思考模式」（Thinking Mode），即在生成最終回應前，先進行長鏈推理（Chain-of-Thought, CoT）。雖然這可能提高複雜問題的答案品質，但在策略遊戲的即時決策場景中，長鏈推理會導致顯著的延遲，甚至觸發超時錯誤。為了解決這一問題，系統透過 `extra_body` 參數傳遞 `{"chat_template_kwargs":{"enable_thinking":false}}`，明確關閉模型的思考標記。

關閉 `enable_thinking` 的主要目的是縮短推論時間並杜絕長鏈推理超時。在 EVALUATION.md 的 Qwen 實驗中，設定 `enable_thinking:false` 後，模型的回應時間大幅減少，使得系統能夠在預設的 `timeout`（120 秒）內完成呼叫。若開啟思考模式，模型可能在生成最終 JSON 前產生數千個 Token 的推理過程，不僅增加了 Token 成本，更極易導致超時。此外，思考模式生成的推理內容通常不適合直接作為遊戲指令的依據，因為它可能包含與遊戲規則無關的泛化推理。透過關閉此功能，系統強制模型直接輸出結構化的 JSON 決策，確保了輸出的相關性與即時性。

延遲抑制不僅是技術優化，更是遊戲體驗的關鍵。在多人線上策略遊戲中，若 LLM 代理的決策時間過長，會導致遊戲回合卡頓，影響其他玩家的體驗。`OpenAIChatCompleter` 中的 `timeout` 參數與 `CircuitBreakerCompleter` 的協作，進一步保障了系統在延遲異常時的穩定性。當模型因思考模式或其他原因導致回應過慢時，超時異常會被捕獲並計入連續錯誤，若達到閾值，斷路器將熔斷，防止系統在無效的等待中耗盡資源。因此，關閉 `enable_thinking` 與合理的超時設定相結合，構成了確保 LLM 代理低延遲、高可用性的雙重保障機制。

## 6.5 異常隔離與斷路器：CircuitBreakerCompleter 防範連續 API 故障，ConfigError 快速暴露設定缺陷

在依賴雲端 API 的系統中，網路不穩定、服務端錯誤或配額耗盡是常見風險。若 LLM 代理在每次決策時都直接呼叫 API，連續的失敗將導致遊戲引擎陷入無效的重試循環，不僅浪費資源，更可能導致遊戲狀態不一致。為此，系統引入了 `CircuitBreakerCompleter`，作為所有 `Completer` 後端的包裝器，實現異常隔離與斷路器保護。`CircuitBreakerCompleter` 維護一個 `consecutive_errors` 計數器，當後端連續發生異常的次數達到 `max_consecutive_errors`（預設為 3 次）時，斷路器狀態轉為 `open`。

一旦斷路器開啟，後續的呼叫將不再觸發實際的 API 請求，而是直接拋出 `BackendUnavailable` 異常。這種設計有效地防止了對故障服務的持續衝擊，避免了因無限重試造成的 API 額度超支與延遲累積。在 `LLMFactionAgent.decide` 方法中，若捕獲到 `BackendUnavailable`，代理將無法產生決策，遊戲引擎可根據此異常採取預設策略（如委任規則 AI 代行），確保遊戲流程不中斷。此外，`CircuitBreakerCompleter` 在成功回應後會重置 `consecutive_errors` 計數器，使系統在服務恢復後能自動閉合斷路器，恢復正常呼叫。

`ConfigError` 在異常處理中扮演了快速暴露設定缺陷的角色。與一般的運行時錯誤不同，`ConfigError` 通常由配置錯誤（如 API Key 格式錯誤）引發，這類錯誤在運行期間不會自行恢復。因此，`CircuitBreakerCompleter` 對 `ConfigError` 採取了特殊的處理策略：一旦捕獲 `ConfigError`，斷路器立即開啟，且不會因後續的重試而自動閉合。這迫使開發者或運維人員必須修正配置錯誤並重新啟動系統，從而避免了因配置問題導致的長期無效呼叫。透過 `CircuitBreakerCompleter` 與 `ConfigError` 的協作，系統實現了對雲端資源的有效保護，確保了在複雜網路環境下的穩定運行與成本可控。

## 本章重點
1. `SYSTEM_PROMPT` 透過嚴格的輸出契約與短碼格式範例，規範 LLM 產生符合遊戲規則的結構化 JSON 指令，並嵌入戰略引導邏輯。
2. `parse_plan` 利用 `json.JSONDecoder.raw_decode` 從夾帶雜訊的文本中提取第一個合法 JSON 物件，並透過別名映射與陣列解包進行參數歸一化，提高容錯性。
3. 多後端 `Completer` 架構解耦了 LLM 代理與具體模型服務，`OpenAIChatCompleter` 處理雲端 API，`DemoCompleter` 支援離線測試，`CommandCompleter` 整合外部命令。
4. 關閉 `enable_thinking` 是抑制延遲的關鍵措施，它防止模型進行長鏈推理，確保在超時限制內快速輸出決策，優化遊戲回合週期。
5. `CircuitBreakerCompleter` 透過連續錯誤計數與斷路器狀態機，防範連續 API 故障對系統的衝擊，避免無效重試與資源浪費。
6. `ConfigError` 用於快速暴露設定缺陷，觸發斷路器立即熔斷，迫使修正配置而非無限重試，確保系統在配置錯誤時的穩定性與可維護性。
7. 異常隔離與斷路器機制共同構成了 LLM 代理的保護網，確保在雲端環境不穩定時，遊戲引擎仍能透過預設策略維持運行。

## 習題
1. 假設 LLM 輸出的 JSON 物件中，`params` 的 `to` 參數被包裹在長度為 1 的陣列中（如 `["beijing"]`），請說明 `parse_plan` 函式如何處理此情況，並指出這會如何影響 `normalized_params` 統計數據。
2. 在 `CircuitBreakerCompleter` 中，若後端連續發生 2 次一般異常（如 `RuntimeError`），第 3 次發生 `ConfigError`，請描述斷路器的狀態變化及後續呼叫的行為。
3. 比較 `OpenAIChatCompleter` 與 `DemoCompleter` 在處理 `enable_thinking` 參數上的差異，並說明為何在 Qwen 實驗中需要透過 `extra_body` 傳遞此參數。
4. 若 LLM 在輸出完整 JSON 物件後，又輸出了第二個 JSON 物件，請解釋 `parse_plan` 中 `raw_decode` 如何處理這種 `Extra data` 情況，並說明這對 API 呼叫成本的影响。
5. 設計一個測試用例，驗證 `SYSTEM_PROMPT` 中關於 `siege_odds` 的戰略引導是否有效。請描述測試情境、預期 LLM 的行為，以及如何透過 `parse_plan` 的輸出驗證該行為。
