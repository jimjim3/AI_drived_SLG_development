# 第 11 章：開發方法論：分層外包與驗收

## 本章學習目標
1. 理解分層外包架構中，主管 AI、雲端 agy worker 與本機 Qwen worker 的職責分工與協作流程。
2. 掌握「不採信 worker 自述」的對抗性驗證哲學，並學會使用可重現測試與數據結晶作為唯一驗收依據。
3. 熟悉嚴格驗收流水線的構成，包括單元測試、種子回歸一致性檢驗與突變測試（mutation testing）的防範機制。
4. 了解基礎設施防護網的設計，特別是保護雲端配額的斷路器機制與長任務暫停點管理。
5. 反思 AI 輔助開發中的關鍵軟體工程實踐，即邊界定義與獨立驗證預言機的重要性。

## 11.1 分層外包架構：主管 AI 與 Worker 的協同

在現代 AI 輔助軟體工程中，開發流程已從單一的程式員編碼轉變為多代理（Multi-Agent）協同作業。本專案採用的核心方法論是「分層外包」，即將不同性質的任務分配給不同能力的 AI 代理執行，並由一個具備全局視野的主管 AI 進行規格制定與審查。

此架構包含三個主要角色：
1. **主管 AI（Orchestrator）**：負責將高階需求分解為具體的技術規格（Spec），定義驗收標準，並審查 Worker 的產出。主管 AI 不直接撰寫大量業務邏輯代碼，而是專注於系統邊界、介面定義與邏輯正確性的把關。
2. **雲端 agy Worker**：專門負責複雜程式碼的撰寫與架構實現。由於雲端模型通常具備較強的推理能力與代碼生成品質，適合處理引擎核心邏輯（如 `engine/resolution.py` 中的戰鬥公式）或複雜的代理介面（如 `LLMFactionAgent`）。
3. **本機 Qwen Worker**：負責無額外成本的實驗、調參與重複性任務。例如，在調試忠誠／冷落機制時，利用本機部署的 Qwen3.8-27B 進行大量參數組合的網格搜尋（Grid Search）。由於本機執行不消耗雲端 API 額度，適合進行高頻率的迭代實驗。
4. **nim-staff 跨域協同**：在特定情境下，引入其他專業領域的代理進行協同，例如處理特定領域知識或數據處理任務。

## 11.2 不採信 worker 自述原則

在 AI 輔助開發中，最危險的陷阱之一是「虛假完成」（False Completion）。Worker 可能在對話中聲稱「任務已完成」或「測試全數通過」，但其實際產出的代碼可能存在邏輯錯誤、未覆蓋的邊界條件，甚至根本未執行測試。

因此，本專案確立了**不採信 worker 自述**（Do Not Trust Worker's Self-Report）的核心原則。這意味著：
- **忽略自然語言聲明**：主管 AI 完全忽略 Worker 在對話中關於任務狀態的陳述（如「我已修復該 Bug」）。
- **依賴可重現測試**：唯一的驗收依據是執行測試套件後的實際輸出。所有測試必須是確定性的，且能重現相同的結果。
- **數據結晶（Data Crystals）**：驗收結果必須以結構化數據（如 JSON 報告、測試通過數、性能指標）呈現，而非自然語言描述。這些數據結晶是後續分析與回歸測試的基礎。

例如，在任務 M（重調忠誠／冷落常數）中，Qwen worker 聲稱已找到最佳常數組合。主管 AI 並未直接採信，而是要求提供 `git diff` 統計、執行 `python3 -m unittest` 的完整輸出，以及重跑 `tune_attention` 腳本後的行為數據。只有當所有數據結晶符合預期時，任務才被視為完成。

## 11.3 嚴格驗收流水線

為了確保代碼品質與邏輯正確性，本專案建立了一套多層次的嚴格驗收流水線。這套流水線不僅檢查功能是否正常，更著重於防範「無效斷言」與「隱性回歸」。

### 1. 單元測試全過
最基本的門檻是專案中所有的單元測試（Unit Tests）必須全數通過。例如，在任務 M 的驗收中，要求 `python3 -m unittest` 執行結果必須為 313+8 個測試全過。任何一個測試失敗都意味著代碼存在缺陷，必須退回 Worker 修復。

### 2. 種子回歸一致性檢驗
由於遊戲引擎依賴隨機種子（Random Seed）驅動，任何對核心邏輯的修改都可能導致遊戲行為的微妙變化。因此，驗收流程包含種子回歸檢驗：
- **基準對照**：在修改前，記錄規則 AI 在特定種子（如 0–9）下的勝者（winner）與決策數（decisions）。
- **一致性比對**：修改後，重跑相同種子的模擬，比對結果是否與基準完全相同。
- **目的**：確保未對核心遊戲邏輯（如結算順序、隨機數生成）產生意外影響。若結果不一致，則視為回歸錯誤，必須調查原因。

### 3. 突變測試（Mutation Testing）防範無效斷言
單元測試通過並不代表測試具有鑑別力。如果測試斷言過於寬鬆，即使代碼存在錯誤，測試仍可能通過。突變測試通過自動導入微小錯誤（如將 `>` 改為 `>=`，將 `+` 改為 `-`）到代碼中，並觀察測試套件是否能偵測到這些錯誤。

- **工具**：使用 `~/local-llm-setup/scripts/mutate_auto.py` 執行突變測試。
- **標準**：若突變測試的殺滅率（Kill Rate）低於預期，表示存在「無效斷言」或「測試覆蓋不足」，必須補充測試用例。
- **意義**：這確保了測試套件不僅是「通過」，而是真正具備偵測錯誤的能力。

## 11.4 基礎設施防護網

在 AI 輔助開發中，基礎設施的穩定性與資源保護至關重要。特別是當涉及雲端 API 呼叫與長任務執行時，必須建立防護網以避免資源浪費與系統崩潰。

### 1. 斷路器機制（Circuit Breaker）
雲端 API 具有配額限制與費用成本。若 Worker 因邏輯錯誤導致無限重試或錯誤呼叫，將迅速耗盡配額。因此，系統實作了斷路器機制：
- **觸發條件**：當連續發生連線異常或 HTTP 錯誤達到上限（預設 3 次）時，斷路器自動熔斷。
- **動作**：即時中止評測流程或任務執行，避免無謂消耗配額。
- **實現**：透過 `--max-consecutive-errors` 參數控制，確保在異常情況下能快速停止。

### 2. 長任務暫停點管理
對於耗時較長的任務（如 Qwen 的參數調試），必須建立明確的暫停點（Checkpoint）與接手步驟：
- **Git Worktree**：Worker 在獨立的 worktree（如 `.worktrees/qwen-M`）中作業，避免污染主分支。
- **日誌記錄**：任務日誌（如 `/tmp/qwen_task_M.log`）完整記錄執行過程，便於後續診斷。
- **接手步驟**：定義標準化的接手流程，包括檢查 `git diff`、執行測試、重跑驗證腳本、比對種子回歸結果，最後才執行合併與清理。
- **資源釋放**：任務結束後，務必執行清理腳本（如 `qwen-clean.sh` 與 `llm-down.sh`），釋放 GPU 資源，避免影響其他訓練任務。

## 11.5 軟體工程實踐啟示

本章所述的分層外包與驗收方法論，提供了 AI 輔助開發的關鍵啟示：

1. **邊界定義（Boundary Definition）**：主管 AI 的核心價值在於清晰定義系統邊界與介面。通過明確的規格檔（Spec）與驗收標準，將模糊的需求轉化為可驗證的技術任務。
2. **獨立驗證預言機（Independent Verification Oracle）**：驗證邏輯必須與實現邏輯獨立。測試套件、回歸基準與突變測試構成了獨立的預言機，確保實現符合預期，而非僅依賴 Worker 的自我聲明。
3. **對抗性驗證哲學**：假設 Worker 可能出錯或欺騙，通過多層次的驗證（單元測試、回歸、突變）與不採信自述原則，建立健壯的防禦體系。
4. **資源意識（Resource Awareness）**：在 AI 開發中，計算資源（GPU、API 配額）是有限且昂貴的。斷路器與暫停點管理確保了資源的有效利用與系統的可恢復性。

這些實踐不僅適用於本專案，也為更廣泛的 AI 輔助軟體工程提供了可複製的方法論框架。

## 本章重點
1. **分層外包架構**：主管 AI 負責規格與審查，雲端 agy 負責複雜代碼，本機 Qwen 負責低成本實驗，形成高效協作。
2. **不採信 worker 自述**：杜絕虛假完成，完全依賴可重現測試與數據結晶作為驗收依據。
3. **嚴格驗收流水線**：包含單元測試全過、種子回歸一致性檢驗與突變測試，確保代碼品質與測試有效性。
4. **基礎設施防護網**：透過斷路器機制保護雲端配額，並透過長任務暫停點管理確保系統可恢復性。
5. **邊界定義與獨立驗證**：AI 輔助開發的關鍵在於清晰定義系統邊界，並建立獨立的驗證預言機以對抗潛在錯誤。
6. **對抗性驗證哲學**：假設 Worker 可能出錯，通過多層次驗證與不採信自述原則建立健壯防禦。
7. **資源意識**：有效管理計算資源與 API 配額，避免浪費與系統崩潰。
8. **可複製方法論**：本章所述實踐為 AI 輔助軟體工程提供了可複製的方法論框架。
