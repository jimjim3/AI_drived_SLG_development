# 第 6 章：LLM 代理

## 本章學習目標

## 6.1 系統提示詞工程：SYSTEM_PROMPT 規範嚴格輸出契約與短碼格式

在將 LLM 整合進遊戲引擎的決策迴圈時，最大的挑戰在於模型輸出的不確定性與遊戲引擎對數據結構的嚴格要求之間的矛盾。遊戲引擎需要確定性的、可驗證的指令結構，而 LLM 的生成過程本質上是概率性的。為了解決這一矛盾，本系統採用結構化提示詞工程（Structured Prompt Engineering），核心在於 SYSTEM_PROMPT 的設計。SYSTEM_PROMPT 不僅僅是角色設定的描述，更是一份嚴格的輸出契約（Output Contract），它明確規定了模型必須輸出的 JSON 結構、參數格式以及業務邏輯約束。

SYSTEM_PROMPT 的首要任務是定義「短碼格式」與參數規範。由於 LLM 可能在長文本中遺失關鍵資訊或產生格式錯誤，提示詞中明確要求輸出只能是一個 JSON 物件，且不得輸出 JSON 以外的文字。具體而言，提示詞詳細列出了 orders、chronicle 與 next_cast 三個字段的結構。其中，orders 是一個陣列，每個元素代表一位武將的行動指令。為了減少解析錯誤，提示詞特別強調 params 的鍵名必須與該武將 legal 清單中的鍵名完全相同，且值為單一字串或數字，不可為陣列。例如，移動指令的 params 中 to 參數必須是字串，而非包含單一元素的陣列。這種嚴格的格式規定直接針對了後續實驗中發現的常見錯誤，如將 to 傳入長度為 1 之陣列或遺漏 to 參數。

此外，SYSTEM_PROMPT 還承擔了戰略引導的職能。它不僅告訴模型「怎麼輸出」，還告訴模型「怎麼思考」。提示詞中明確告知模型金錢與兵力有限、指令依序結算，並引入了忠誠度機制：久未被點名且動作非 rest 的武將忠誠會下降並可能出奔。為了引導模型進行合理的軍事決策，提示詞引入了 siege_odds（勝算比）的概念，明確指出勝算比是攻方戰力與守方戰力之比，並警告實戰有約 ±15% 的隨機波動，比值低於 1.3 的出征很可能失敗。這種將業務邏輯嵌入提示詞的做法，使得模型在生成指令時能夠自發地避開高風險行動，從而提高了指令的接受率與戰略合理性。

## 6.2 容錯 JSON 解析：parse_plan 與 raw_decode 從夾帶雜訊之生成文本中精確提取第一個合法 JSON 物件

儘管 SYSTEM_PROMPT 嚴格規定了輸出格式，LLM 仍可能因上下文長度限制、模型本身的隨機性或溫度參數（temperature）的影響，輸出夾帶雜訊的文本。這些雜訊可能包括 Markdown 代碼塊標記（如 ```json）、解釋性文字，甚至是多個 JSON 物件。為了應對這種不確定性，parse_plan 函式採用了一種魯棒的解析策略，其核心是 Python 標準庫 json.JSONDecoder 的 raw_decode 方法。

raw_decode 與標準的 json.loads 不同，它不會嘗試解析整個輸入字符串，而是從指定的索引位置開始，解析出第一個合法的 JSON 值，並返回該值及其結束位置。這使得 parse_plan 能夠精確地從生成文本中提取第一個合法的 JSON 物件，而忽略其後的任何多餘內容。在實作中，parse_plan 首先掃描輸入文本，尋找第一個 { 或 [ 的位置。如果找到 [，則嘗試解析為陣列，但隨後會檢查頂層是否為 dict，因為 FactionPlan 要求頂層必須是物件。如果找到 {，則直接從該位置開始調用 raw_decode。這種策略有效地解決了實驗中觀察到的 Extra data 問題，即模型在輸出完整 JSON 物件後，在尾端多寫了第二個物件或補充文字，導致標準解析器失敗。

除了處理多餘內容，parse_plan 還具備強大的參數正規化（Normalization）能力。LLM 可能會使用不同的鍵名來表示相同的語義，例如使用 target、destination 或 city 來代替 to，或使用 troop、soldiers 或 army 來代替 troops。parse_plan 定義了 TO_ALIASES 與 TROOPS_ALIASES 常數，並在解析過程中自動將這些別名映射到標準鍵名。此外，它還會處理數值型別問題，將整數值的浮點數（如 10.0）轉換為整數（10），並處理長度為 1 的陣列，將其解包為單一值。這些正規化操作不僅提高了解析的成功率，還通過 stats 參數記錄了正規化的次數，為後續的模型行為分析提供了數據支持。

## 6.3 多後端 Completer 架構：OpenAIChatCompleter、離線 DemoCompleter 與外部命令後端

為了實現系統的可擴展性與可測試性，LLM 代理採用了多後端 Completer 架構。Completer 被定義為一個可呼叫物件（Callable[[str, str], str]），接受系統提示詞與使用者提示詞，並返回生成文本。這種抽象使得代理層與具體的 LLM 實現解耦，允許在開發、測試與生產環境中靈活切換不同的後端。

OpenAIChatCompleter 是生產環境中的主要後端，它通過標準庫 urllib 呼叫 OpenAI 相容的 REST API。其設計重點在於資源管理與錯誤處理。它支持配置 base_url、model、api_key_env、timeout、temperature 與 max_tokens 等參數。特別值得注意的是，它支持 extra_body 參數，允許注入額外的 API 參數，例如在本地部署 Qwen 模型時，通過 extra_body 傳遞 chat_template_kwargs 以控制 enable_thinking 行為。在錯誤處理方面，OpenAIChatCompleter 會捕獲 HTTP 錯誤與網絡錯誤，並將其包裝為 RuntimeError，同時對 API 金鑰進行脫敏處理，防止敏感資訊洩露。

DemoCompleter 是一個離線示範後端，用於在沒有 LLM 訪問權限的環境中進行功能測試與演示。它通過解析使用者提示詞中的 JSON 狀態數據，模擬 LLM 的決策過程。DemoCompleter 採用簡單的策略：為每位武將選擇 legal 清單中第一個非 rest 的行動，並生成固定的 chronicle 與 next_cast。這種確定性的行為使得開發者能夠快速驗證引擎的結算邏輯與 UI 渲染，而無需等待雲端 API 的回應。此外，還存在 CommandCompleter，它通過執行外部子進程來生成完成文本，適用於需要調用本地腳本或特定 CLI 工具的場景。

## 6.4 思考標記與延遲抑制：關閉 enable_thinking 縮短推論時間，杜絕長鏈推理超時

在本地部署大語言模型（如 Qwen3.8-27B）時，推論延遲（Inference Latency）是一個關鍵的性能指標。許多現代 LLM 支持「思考模式」（Thinking Mode），即模型在生成最終答案前，會先輸出一段長鏈推理（Chain-of-Thought, CoT）文本。雖然思考模式可以提高複雜任務的準確性，但它會顯著增加 token 消耗與推論時間。在即時策略遊戲（RTS/SLG）的回合制決策中，過長的推論時間會導致遊戲體驗中斷，甚至觸發超時錯誤。

為了解決這一問題，系統通過 enable_thinking 參數來控制模型的思考行為。在 OpenAIChatCompleter 中，enable_thinking 並非直接作為 API 參數，而是通過 extra_body 機制傳遞給底層服務。例如，在本地 llama-server 部署 Qwen 模型時，通過設定 --extra-body-json '{"chat_template_kwargs":{"enable_thinking":false}}'，可以明確關閉模型的思考模式。關閉 enable_thinking 後，模型將直接生成最終答案，從而大幅縮短推論時間。實驗數據顯示，關閉思考模式後，每回合的 LLM 呼叫延遲從數秒級別降低至毫秒級別，有效杜絕了長鏈推理超時問題。

此外，temperature 與 max_tokens 參數的調優也是延遲抑制的重要組成部分。temperature 設定為 0.2，確保模型輸出的穩定性與一致性，減少因隨機性導致的重試需求。max_tokens 設定為 900，限制了模型輸出的最大長度，防止模型生成過長的解釋性文本或冗餘的 JSON 結構。這些參數的組合使用，使得系統在保持決策質量的同時，實現了低延遲、高可靠的 LLM 代理服務。

## 6.5 異常隔離與斷路器：CircuitBreakerCompleter 防範連續 API 故障，ConfigError 快速暴露設定缺陷

在雲端 API 環境中，網絡抖動、服務端過載或配額耗盡等問題可能導致連續的呼叫失敗。如果系統在這種情況下持續重試，不僅會浪費 API 額度，還可能導致遊戲狀態長時間掛起。為了防範這種情況，系統引入了 CircuitBreakerCompleter，實現了斷路器模式（Circuit Breaker Pattern）。

CircuitBreakerCompleter 包裹了一個內部 Completer（inner），並維護一個連續錯誤計數器（consecutive_errors）。當內部 Completer 拋出異常時，斷路器會增加計數器。如果計數器達到預設的 max_consecutive_errors（預設為 3），斷路器將進入「開啟」（Open）狀態。在開啟狀態下，CircuitBreakerCompleter 不再調用內部 Completer，而是直接拋出 BackendUnavailable 異常。這種機制能夠快速中斷無效的 API 呼叫，保護雲端資源，並允許上層應用（如評測腳本）優雅地終止當前種子並輸出部分統計數據。

ConfigError 是另一種重要的異常類型，用於快速暴露設定缺陷。與一般的運行時錯誤不同，ConfigError 通常由不可恢復的配置問題引起，例如 API 金鑰缺失、格式錯誤或環境變數未設定。在 OpenAIChatCompleter 中，如果檢測到 API 金鑰包含非 ASCII 字元或空白字元，將直接拋出 ConfigError。這種異常不會被斷路器計入連續錯誤，而是直接向上層傳播，迫使開發者立即修正配置，從而避免了因配置錯誤導致的長時間無效重試。這種異常隔離策略確保了系統在面對不同類型的故障時，能夠採取最適當的應對措施，提高了整體的健壯性與可維護性。

## 本章重點
1. SYSTEM_PROMPT 通過定義嚴格的 JSON 輸出契約與戰略引導邏輯，有效約束了 LLM 的生成行為，提高了指令的結構化程度與合理性。
2. parse_plan 函式利用 json.JSONDecoder.raw_decode 實現了容錯 JSON 解析，能夠從夾帶雜訊的文本中精確提取第一個合法 JSON 物件，並具備強大的參數正規化能力。
3. 多後端 Completer 架構通過抽象化 LLM 呼叫介面，支持 OpenAIChatCompleter、DemoCompleter 與 CommandCompleter 等多種實現，實現了開發、測試與生產環境的靈活切換。
4. 通過關閉 enable_thinking 參數並調優 temperature 與 max_tokens，系統有效縮短了本地模型的推論時間，杜絕了長鏈推理超時問題，提升了遊戲的即時性。
5. CircuitBreakerCompleter 實現了斷路器模式，通過監控連續錯誤次數，在 API 持續故障時快速熔斷，保護了雲端資源並避免了無效重試。
6. ConfigError 異常用於快速暴露設定缺陷，確保開發者能夠及時發現並修正配置問題，提高了系統的健壯性與可維護性。
