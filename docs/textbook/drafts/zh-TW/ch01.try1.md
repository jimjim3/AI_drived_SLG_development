# 第 1 章：動機：為什麼讓 LLM 當君主

## 本章學習目標

- 理解傳統全 LLM 代理架構在大型策略遊戲中面臨的 Token 爆炸困境，並量化其成本差異。
- 掌握「君主分層決策」的核心構想，區分戰略層、執行層與事件驅動層的職責邊界。
- 熟悉勢力敘事（Faction Narrative）模式與出場名單機制，了解如何將輸入 Token 與勢力規模解耦。
- 釐清遊戲機制與公有領域文獻在法律上的保護邊界，建立獨立研發的合規基礎。
- 預覽全書章節地圖，理解從世界規則、注意力經濟到安全網與實證數據的邏輯脈絡。

## 1.1 全 LLM 代理的虛妄：Token 爆炸困境

在大型多人線上策略遊戲（SLG）或回合制策略遊戲中，若採用最直覺的「全 LLM 代理」架構，即讓遊戲中的每一位角色（如武將）在每一回合都獨立呼叫大型語言模型（LLM）進行決策，將面臨嚴峻的成本與延遲挑戰。這種架構假設每個角色都是獨立的智慧體，需要根據當前狀態做出反應。然而，在規模化場景下，這種假設會導致計算資源的指數級增長。

以一個典型的三國題材遊戲為例，假設遊戲中有 20 個勢力，每個勢力平均擁有 5 座城池，總共約 400 位武將。若採用「每位武將每回合都問」的設計，每回合需要進行約 420 次 LLM 呼叫（考慮到部分武將可能處於閒置或特殊狀態）。假設每次呼叫的平均 Token 消耗（包含輸入 Prompt 與輸出回應）約為 1,500 tokens，則單回合的 Token 消耗將高達約 630k（630,000）tokens。

若一局遊戲標準長度為 300 回合，則總 Token 消耗將達到 1.9 億 tokens 以上。對於商用 LLM API 而言，這意味著巨大的經濟成本；對於本地部署的模型而言，這意味著極高的延遲與硬體負載。更關鍵的是，延遲問題無法並行解決：雖然不同武將的決策可以並行執行，但每回合的總延遲取決於最慢的那一次呼叫。在 400 人規模下，即使並行處理，網路抖動與模型推理時間的累積仍會導致單回合延遲難以控制在玩家可接受的範圍內（通常需小於幾秒鐘）。

此外，全 LLM 代理還存在「資訊過載」與「注意力分散」的問題。LLM 的注意力機制在處理長上下文時效能會下降，若將整個遊戲世界的狀態都塞入每個武將的 Prompt 中，不僅 Token 成本高昂，且模型可能無法有效聚焦於對該武將決策真正關鍵的資訊。因此，直接讓所有角色都具備 LLM 決策能力，在工程上是不切實際的，在經濟上是不可承受的。

## 1.2 相關研究借鏡：從 CivAgent 到 vox-deorum

在探討分層決策之前，有必要回顧相關領域的研究與開源專案，以理解現有技術的得失與邊界。

在策略遊戲 AI 領域，CivAgent 是一個基於開源遊戲 Unciv 的 LLM 數位玩家專案。它展示了 LLM 在自然語言外交與高層戰略規劃上的潛力，特別是在透過 Discord 介面進行即時外交談判時。然而，CivAgent 主要聚焦於外交與宏觀層面，對於微觀操作（如單位移動、資源開發的細節）仍依賴底層規則或簡化邏輯。

CivRealm 則是發表於 ICLR 2024 的研究，探討在 Freeciv 環境下使用強化學習（RL）與 LLM 代理進行對戰。其結論指出，LLM 在完整遊戲流程中仍表現吃力，特別是在需要長期規劃與精細操作的情境下。這提醒我們，單純依靠 LLM 的通用推理能力不足以應對複雜策略遊戲的所有層面，必須引入分層架構與規則 AI 作為補位。

最具啟發性的是 vox-deorum 專案（論文 arXiv:2512.18564）。該專案在《文明 V》中實證了一種分層架構：LLM 只負責宏觀戰略（如國家發展方向、外交態度），而微觀操作（如城市發展、軍隊調度）交給原本的演算法 AI。實驗結果顯示，這種架構能跑完 400 回合，且勝率與原遊戲 AI 持平。這幾乎就是本專案「分層」理念的實證基礎：LLM 適合做「君主」，不適合做「士兵」。

## 1.3 勢力敘事與層級切分

為了解決 Token 爆炸問題，本專案提出「君主分層決策」策略，並引入「勢力敘事」模式。核心思想是：將整個勢力的決策權上收至「君主」層級，而非分散至每一位武將。

具體而言，分層結構定義為：
1. **君主（Ruler）**：每回合呼叫一次 LLM，負責制定戰略方向、外交政策與各城的角色定位（前線/後勤/開發）。
2. **太守（Governor）**：每回合每城呼叫一次（或由君主指令隱含決定），負責將城內武將分派到具體工作。
3. **武將（Officer）**：事件驅動，僅在特定情境（如戰場戰術、被策反、談判）下才由 LLM 介入，其餘時間由規則 AI 自動執行。

「勢力敘事」模式進一步將「君主 + 太守」合併為每勢力每回合單次呼叫。LLM 以「史官」或「說書人」的視角，為該勢力寫出這一回合的紀事，並同時輸出結構化的指令（`orders`）與下一回合的出場名單（`next_cast`）。

這種設計有三大優勢：
1. **成本可控**：每勢力每回合僅一次呼叫，Token 消耗與勢力數量線性相關，而非與武將數量相關。
2. **敘事沉浸感**：LLM 生成的紀事提供了遊戲的敘事層面，讓玩家感受到歷史的流動。
3. **注意力經濟**：透過 `next_cast` 機制，LLM 決定下一回合要詳細關注哪些武將，引擎則只展開這些人的詳細資料。未被點名的武將由規則 AI 自動委任代理，確保遊戲流程不中斷。

這種「層級切分」將 LLM 的算力集中在高價值決策上，而將低價值的高頻操作交給確定性的規則引擎，符合「讓 LLM 當君主」的核心構想。

## 1.4 智慧財產與公開領域邊界

在開發基於歷史題材的遊戲時，智慧財產權（IP）的邊界是必須面對的法律問題。本專案選擇以《三國演義》為題材，但必須釐清哪些內容受保護，哪些屬於公有領域。

首先，遊戲規則與機制本身不受著作權保護。根據「idea/expression 二分法」（Idea/Expression Dichotomy），遊戲的玩法、機制、數值平衡等屬於「觀念」（Idea），不受著作權保護；只有具體的程式碼、美術素材、音樂、文字劇本等「表達」（Expression）才受保護。因此，開發一款具有類似《三國志》玩法的遊戲，只要不複製原作的程式碼與資產，在法律上是可行的。

其次，歷史文獻的版權狀態。羅貫中的《三國演義》與陳壽的《三國志》原文均已完成數百年，屬於「公有領域」（Public Domain）。這意味著可以自由使用其中的人物、事件、對話與情節，無需支付版權費。這為獨立研發提供了合法的基石，允許開發者基於歷史事實與文學創作進行再創。

然而，需要注意的是，現代遊戲公司（如 KOEI）對其遊戲中的武將數值表、美術設計、程式碼等享有版權。因此，本專案採取「獨立研發」策略：
1. **數值自訂**：不照抄 KOEI 的武將數值，而是基於《三國演義》事蹟，透過規則或 LLM 推導出獨立的數值體系。
2. **美術原創**：使用 AI 生成或程式生成的頭像與地圖，並在 README 中註明來源與授權。
3. **程式碼原創**：所有遊戲引擎與 AI 代理程式碼均為原創，不 fork 任何受版權保護的遊戲專案。

## 1.5 本書結構與章節地圖

本章作為全書開篇，確立了「讓 LLM 當君主」的動機與基礎。後續章節將依序展開設計、實作與實驗。

- **第 2 章 遊戲世界與規則**：詳細定義遊戲的地圖、城池、武將屬性與回合結算規則，建立確定性的遊戲引擎基礎。
- **第 3 章 設計原則**：闡述「引擎是真理來源」、「AI 是可替換插件」等核心設計原則，以及資訊感知邊界（戰爭迷霧）的設計。
- **第 4 章 勢力敘事與注意力經濟**：深入探討勢力敘事模式的 Prompt 設計、出場名單機制（`next_cast`）與「受冷落」玩法，分析 Token 成本與敘事品質的平衡。
- **第 5 章 引擎實作與安全網**：介紹 Python 遊戲引擎的實作細節，包括合法行動產生、決策驗證、結算邏輯與異常處理的安全網機制。
- **第 6 章 LLM 代理**：探討 LLM 代理的介面設計、Prompt 工程、結構化輸出解析與多後端支援（OpenAI API、本機 CLI 等）。
- **第 7 章 忠誠、冷落、抗旨與出奔**：設計並實作忠誠度系統、抗旨判定機制與武將出奔事件，將技術限制轉化為遊戲玩法。
- **第 8 章 評測方法**：建立客觀的評測體系，包括勝率、Token 消耗、敘事一致性等指標，並介紹 Headless 模擬與確定性重播技術。
- **第 9 章 實驗一：Gemini 的三個階段**：展示使用 Gemini 模型進行小規模實驗的結果，分析不同 Prompt 策略對決策品質的影響。
- **第 10 章 實驗二：本機 Qwen 大規模實驗**：展示使用本機部署的 Qwen 模型進行大規模實驗的結果，評估成本與效能的取捨。
- **第 11 章 開發方法論：分層外包與驗收**：總結開發過程中的方法論，包括如何分層外包任務、如何驗收 AI 代理的輸出品質。
- **第 12 章 已知缺陷與開放問題**：誠實記錄專案的已知限制與未解決問題，如休息比例偏高、勝率不對稱等。
- **第 13 章 下一步與實驗路線圖**：規劃未來的研究方向，包括前端介面、更複雜的 AI 策略與多模型對戰。

全書旨在提供一個完整的、可重現的、基於分層 AI 決策的策略遊戲開發範例，為讀者提供從理論到實作的參考。

## 本章重點

- 全 LLM 代理架構在 400 人規模下每回合消耗約 630k tokens，一局 300 回合耗費上億 tokens，成本與延遲無法承受。
- vox-deorum 等研究實證了「LLM 負責宏觀、規則 AI 負責微觀」的分層架構可行性，勝率可與原 AI 持平。
- 勢力敘事模式將全勢力決策壓縮為每回合單次呼叫，透過 `orders` 與 `chronicle` 輸出，結合 `next_cast` 機制控制輸入 Token。
- 遊戲規則與機制不受著作權保護，歷史文獻如《三國演義》屬公有領域，為獨立研發提供合法基礎，但需避免複製現代遊戲的數值與資產。
- 分層決策架構將 Token 消耗從 ~630k 降至 ~30k，實現了成本與效能的平衡，同時保留了 LLM 的敘事與戰略優勢。
- 本書後續章節將從遊戲規則、設計原則、引擎實作、LLM 代理、評測方法到實驗結果，系統性呈現分層 AI 決策策略遊戲的開發過程。

## 習題

1. 假設遊戲規模擴大至 50 個勢力，每勢力 10 城，共 500 位武將。若採用「每位武將每回合都問」架構，每回合 Token 消耗將約為多少？若採用「勢力敘事」架構（每勢力每次 3k tokens），每回合 Token 消耗將約為多少？計算兩者差距。
2. 在「勢力敘事」模式中，若 LLM 未指定 `next_cast`，引擎將如何處理未被點名的武將？這種機制對遊戲的公平性與玩家體驗有何潛在影響？
3. 根據「idea/expression 二分法」，為什麼開發一款玩法類似《三國志》但程式碼與美術原創的遊戲在法律上是可行的？請舉例說明哪些元素屬於「idea」，哪些屬於「expression」。
4. 比較「君主 + 太守批次」與「勢力敘事」兩種架構的優缺點。在什麼情境下，「君主 + 太守」可能比「勢力敘事」更適合？
5. 若要在本專案中實作「抗旨」機制，請設計一個簡單的判定公式，包含忠誠度、野心與君主威望三個變數，並說明如何將 LLM 的輸出與引擎的判定結果結合，以生成合理的「抗旨」敘事。
