# 第 4 章：勢力敘事與注意力經濟

## 本章學習目標
- 理解分層 AI 決策中「勢力敘事模式」的運作原理，以及它如何將 Token 預算從線性增長轉化為常數控制。
- 掌握 `FactionPlan` 的結構化三元組（`orders`、`chronicle`、`next_cast`）及其在引擎驗證與執行中的角色。
- 分析「出場名單聚光燈」（`CAST_LIMIT`）與「委任代理」機制如何互補，以解決大規模勢力下的決策瓶頸。
- 探討戰爭迷霧（Fog of War）與邊境（`frontier`）機制如何限制情報輸入量，並符合古代戰略常理。
- 認識引擎強制介入（`forced`）機制如何解決 LLM 的注意力盲區，確保突發事件不被忽視。

## 4.1 回合時序架構：收入結算、隨機順序洗牌、視圖生成、計畫制定、指令執行與委任代理

在分層 AI 決策的回合制策略遊戲（SLG）中，單一回合的執行流程被嚴格定義為一條確定性的時序鏈。這不僅是為了確保遊戲狀態的可重現性，更是為了在 LLM 決策與引擎執行之間建立清晰的責任邊界。根據設計文件與實作現況，一個標準回合的時序架構包含以下關鍵階段：收入結算、隨機順序洗牌、視圖生成、計畫制定、指令執行與委任代理。

[[FIG:f04_turn_sequence]]

如圖 4-1 所示，回合伊始，引擎首先進行**收入結算**。這一步驟依據各城池的農業（`agriculture`）與商業（`commerce`）數值，計算當回合的糧食與黃金產出，並更新 `CityState` 中的資源欄位。此階段完全由規則驅動，不涉及任何 AI 決策，確保了經濟基礎的客觀性。

緊接著是**隨機順序洗牌**。為了消除多勢力同時決策時可能產生的順序偏差，引擎會對所有存活勢力的 ID 進行隨機洗牌。這種隨機性並非為了增加不可預測性，而是為了在對稱條件下保持公平性，並避免先行動者獲得資訊優勢。在實作中，這通常通過固定種子的亂數生成器實現，以確保日誌重播時的確定性。

隨後進入**視圖生成**階段。引擎根據當前遊戲狀態，為每個勢力構建一個受限的視圖（`FactionView`）。這一過程是注意力經濟的核心環節：引擎決定哪些資訊對該勢力是「可見」的。這包括己方城池的詳細狀態、相鄰敵方前線城池的有限情報（`frontier`）、以及上回合被指定為出場名單的武將詳細資料。視圖生成嚴格遵循「每層只看得到它應該知道的事」的原則，將戰爭迷霧具體化為資料結構的過濾。

在視圖準備就緒後，**計畫制定**階段開始。對於採用 LLM 代理的勢力，引擎將 `FactionView` 序列化後提交給模型，要求其輸出一個 `FactionPlan`。這個計畫包含了戰術指令（`orders`）、史書敘事（`chronicle`）以及下回合的聚光名單（`next_cast`）。LLM 在此階段扮演「君主」的角色，基於有限的情報做出戰略判斷。

計畫制定完成後，進入**指令執行**階段。引擎對 `FactionPlan` 中的 `orders` 進行逐條驗證。驗證過程包括檢查指令的合法性（如參數範圍、資源成本、行動可行性）。合法的指令被執行，非法的指令被拒絕並記錄在 `rejected` 欄位中，這些拒絕原因將作為反饋（`feedback`）納入下一回合的視圖中，形成閉環學習。

最後是**委任代理**階段。這是分層架構中至關重要的一環。對於未被 LLM 在 `orders` 中點名的存活武將，引擎不會讓其閒置，而是自動將決策權委託給一個預設的規則型代理（`RuleBasedAgent`，通常設定為 "balanced" 模式）。這些被委任的武將將根據規則邏輯執行最優行動（如開發、訓練或休整）。這種機制確保了即使 LLM 只能關注少數重點人物，整個勢力的所有資源仍能保持高效運轉，避免了因注意力分散而導致的資源浪費。

## 4.2 勢力計畫 FactionPlan：結構化三元組包含 orders（戰術指令）、chronicle（史書敘事）與 next_cast（下回合聚光名單）

`FactionPlan` 是 LLM 代理在每一回合輸出的核心資料結構，定義於 `schema.py` 中。它是一個凍結的資料類（frozen dataclass），包含三個主要欄位：`orders`、`chronicle` 與 `next_cast`。這三個欄位共同構成了一個結構化的三元組，分別對應戰術執行、敘事沉浸與注意力管理。

```python
@dataclass(frozen=True)
class FactionPlan:
    orders: tuple = ()
    chronicle: str = ""
    next_cast: tuple = ()
```

**`orders`（戰術指令）**：這是一個元組，包含了一系列具體的行動指令。在早期設計構想中，曾考慮過使用精簡的短碼 DSL（Domain-Specific Language）來表示指令，例如 `"xuchang: 荀彧 develop_agri"`。然而，實際實作為了避免自然語言或 DSL 解析的不確定性，直接採用了結構化 JSON 格式。每個指令是一個字典，包含 `officer`（武將 ID）、`action`（動作類型，如 `develop_agri`、`recruit`、`move`）、`params`（參數，如兵力、目的地）與 `memo`（簡短註記，長度不超過 20 字）。引擎在執行前會透過 `validate_decision` 函式對這些指令進行嚴格的型別、參數範圍與成本驗證。這種結構化設計確保了 LLM 輸出的可預測性與可驗證性。

**`chronicle`（史書敘事）**：這是一個字串欄位，用於記錄該回合的歷史敘事。設計文件指出，正式史書理應在結算後書寫，以避免「文中攻下洛陽、實際上敗退」的矛盾。然而，目前的實作現況下，`chronicle` 仍由 LLM 在回合決策當下與 `orders` 一併輸出，屬於「事前意圖記述」。雖然這在事實一致性上存在潛在風險，但它提供了極高的沉浸感，讓玩家能即時看到勢力的動態。長度限制為 300 字（`CHRONICLE_MAX = 300`），以控制 Token 成本。

**`next_cast`（下回合聚光名單）**：這是一個元組，包含 LLM 指定的下一回合要詳細關注的武將 ID 列表。這是注意力經濟機制的關鍵輸出。LLM 根據本回合的戰略需求，決定哪些武將需要在下一回合的輸入中被展開詳細資料。這些 ID 將直接影響下一回合 `select_cast` 的執行結果。

`FactionPlan` 的設計體現了「結構化意圖下傳」的原则。LLM 不需要處理每一個武將的細節，而是通過 `orders` 處理重點，通過 `next_cast` 管理注意力，而將其餘部分交給引擎的委任機制。這種分離使得 LLM 的輸出既精簡又高效，同時保留了戰略層次的自由度。

## 4.3 出場名單聚光燈 CAST_LIMIT：上限 6 人限制，其餘人員轉為輕量名冊與自動委任

在大型策略遊戲中，一個勢力可能擁有數十甚至上百名武將。如果每回合都將所有武將的詳細狀態輸入 LLM，Token 成本將呈線性增長，且會導致模型注意力分散。為了解決這個問題，設計引入了「出場名單聚光燈」（Cast Spotlight）機制，並設定了一個硬性上限 `CAST_LIMIT = 6`。

[[FIG:f05_view_blocks]]

如圖 4-2 所示，`FactionView` 由六大組成區塊構成，其中 `cast` 區塊專門用於存放出場名單的詳細資料。`select_cast` 函式負責從所有存活武將中選出最多 6 人進入這個區塊。選擇優先順序如下：
1. **`forced`**：引擎強制插入的武將（如遭受圍城或被俘虜者）。
2. **`requested`**：LLM 在上回合 `next_cast` 中指定的武將。
3. **各城最強**：每個己方城池中綜合能力值（`politics` + `war` + `leadership`）最高的武將。
4. **其餘排序**：剩餘武將按綜合能力值降序排列，直到填滿 6 人上限。

這 6 人將獲得完整的詳細資料，包括屬性、忠誠度、野心、冷落值（`neglect`）以及合法的行動清單（`legal`）。這種「聚光燈」效應確保了 LLM 的注意力集中在最關鍵的人物上。

與此同時，未被選入出場名單的武將並不會從視圖中消失，而是轉為**輕量名冊**（`roster`）。`roster` 是一個字典，以城池 ID 為鍵，值為該城中未出場武將的名字元組。例如：`"chenliu": ("李典", "樂進", "于禁")`。這種輕量表示法僅佔用極少的 Token（每人約 3 tokens），讓 LLM 知道這些人的存在，並可以在 `orders` 中點名他們（儘管他們不會在當回合的輸入中展開詳細資料，引擎會在執行時根據規則或預設值處理）。

**聚光燈與委任代理的互補關係**是此機制的核心。聚光燈機制限定了 LLM 的「認知負載」，使其能專注於戰略重點；而委任代理機制則填補了聚光燈之外的「執行空白」。當 LLM 在 `orders` 中未點名某位武將時，該武將即被視為「被委任」，由 `RuleBasedAgent` 自動決策。這種互補確保了：
1. **Token 效率**：輸入量不隨勢力規模成長，主要取決於 `CAST_LIMIT` 與 `roster` 的名字數量。
2. **決策完整性**：每位武將每回合皆有行動，維持 `valid == decisions` 的完整性。
3. **戰略彈性**：LLM 可以通過 `next_cast` 動態調整關注點，而無需擔心其他武將的基礎運作。

## 4.4 戰爭迷霧與邊境 frontier：僅展示相鄰敵城情報，限制情報輸入量並符合古代戰略常理

戰爭迷霧（Fog of War）是策略遊戲的基本機制，旨在模擬資訊不對稱。在本系統的實作中，戰爭迷霧不僅是遊戲機制，更是控制 LLM 輸入 Token 的重要手段。`build_faction_view` 函式在構建視圖時，嚴格限制了敵方城池的資訊可見性。

具體而言，勢力只能看見：
1. **己方城池**：所有詳細狀態（農業、商業、防禦、黃金、糧食、兵力、鄰接關係）。
2. **邊境（`frontier`）**：僅限於與己方城池相鄰的敵方城池。對於這些邊境城池，視圖僅提供有限的情報，包括：城池 ID、名字、所有者、兵力（`troops`）、防禦值（`defense`）以及相鄰的己方城池 ID（`adjacent_to`）。
3. **非相鄰敵城**：完全隱蔽，不出現在視圖中。

這種設計有兩個主要優點：
1. **限制情報輸入量**：隨著遊戲進行，勢力領土擴張，邊境城池數量通常遠少於敵方總城池數量。這確保了輸入的敵方情報量保持在可控範圍內，避免了因情報過多而導致的 Token 浪費與注意力分散。
2. **符合古代戰略常理**：在古代戰爭中，君主通常無法即時掌握遠方敵城的詳細情況，只能依賴邊境的情報與細作。這種限制增強了遊戲的真實感與策略深度，迫使玩家基於有限的情報進行推斷與決策。

此外，`frontier` 區塊還提供了鄰接關係資訊，幫助 LLM 理解地形與戰略位置。例如，如果一個邊境城池與多個己方城池相鄰，它可能成為重點防禦或進攻目標。這種結構化的邊境資訊，使得 LLM 能更有效地進行戰略規劃。

## 4.5 引擎強制介入 forced：突發事件強制登入聚光燈，解決 LLM 注意力盲區

LLM 的決策基於上一回合的輸入，因此它無法預知本回合發生的突發事件。如果僅依賴 LLM 自己選擇的 `next_cast`，可能會導致對新發生的關鍵事件（如城池被圍、武將被俘）視而不見，從而做出不合邏輯的決策。為了解決這一「注意力盲區」，引擎引入了**強制介入**（`forced`）機制。

`forced_cast` 函式負責識別需要強制加入出場名單的武將。目前實作中，強制介入的條件包括：
1. **圍城事件**：如果某位武將所在的城池正遭受敵方圍攻（`action == "siege"` 且 `faction_id != current_faction`），該武將將被強制加入名單。
2. **被俘事件**：如果某位武將在本回合被俘虜（`captured_officers` 中包含該武將 ID），也將被強制加入名單。
3. **冷落請願**（未完全實作）：設計中還包含對連續多回合未被點名且忠誠度較低的武將進行強制插入，以觸發「毛遂自薦」事件。目前實作中，此部分僅在 `forced_cast` 函式中保留了邏輯框架，但具體的冷落機制（如忠誠下降、出奔）尚未完全落地。

強制介入的武將將優先於 `requested` 名單進入 `cast` 區塊，確保 LLM 在下一回合能立即看到這些突發事件的詳細資訊。這種機制不僅解決了注意力盲區，還增強了遊戲的戲劇張力。例如，當一座城池被圍時，引擎強制將守將加入名單，LLM 必須在下一回合做出防禦或撤退的決策，而不是繼續專注於內政開發。

**`forced` 機制的意義**在於它體現了「引擎是唯一的真理來源」這一核心原則。引擎不僅驗證 LLM 的決策，還主動介入以確保遊戲邏輯的完整性與合理性。通過強制介入，引擎確保了關鍵事件不會被 LLM 的注意力機制所忽視，從而維持了遊戲的敘事連貫性與戰略嚴謹性。

## 本章重點
- 回合時序架構包含收入結算、隨機洗牌、視圖生成、計畫制定、指令執行與委任代理六個階段，確保了遊戲的確定性與公平性。
- `FactionPlan` 是 LLM 的核心輸出，包含 `orders`（結構化戰術指令）、`chronicle`（事前敘事）與 `next_cast`（下回合聚光名單）三個欄位。
- `CAST_LIMIT = 6` 的出場名單聚光燈機制，將 LLM 的注意力集中在最關鍵的 6 位武將上，其餘人員轉為輕量名冊（`roster`）。
- 聚光燈與委任代理互補：聚光燈管理注意力，委任代理（`RuleBasedAgent`）確保未點名武將的基礎運作，實現 Token 效率與決策完整性的平衡。
- 戰爭迷霧通過 `frontier` 區塊限制敵方情報輸入，僅展示相鄰敵城的有限資訊，符合古代戰略常理並控制 Token 成本。
- 引擎強制介入（`forced`）機制將突發事件（如圍城、被俘）的武將強制加入出場名單，解決 LLM 的注意力盲區，確保關鍵事件不被忽視。

## 習題
1. 假設一個勢力擁有 20 名武將，其中 5 名被 LLM 在 `next_cast` 中指定，2 名因圍城被強制加入，其餘 13 名未被點名。請描述 `select_cast` 函式在下一回合如何構建 `cast` 區塊，並說明這 13 名未被點名武將的行動是如何決定的。
2. 比較「每位武將每回合都問 LLM」與「勢力敘事模式 + 聚光燈」兩種設計在 Token 成本上的差異。假設 20 個勢力，每勢力 5 城，估算兩種設計在 300 回合遊戲中的總 Token 消耗量級。
3. 在 `FactionPlan` 中，`chronicle` 目前是在決策時產出的「事前意圖」，而非結算後的「正式史書」。請分析這種設計可能導致的敘事與事實不一致問題，並提出一種改進方案，使 `chronicle` 能更準確地反映結算結果。
4. 解釋 `frontier` 區塊中 `adjacent_to` 欄位的意義，並說明它如何幫助 LLM 進行戰略決策。如果移除該欄位，對 LLM 的決策品質可能產生什麼影響？
5. 設計一個實驗，驗證 `forced` 機制對 LLM 決策合理性的影響。請描述實驗的變量、控制組與實驗組的設置，以及衡量決策合理性的指標。
