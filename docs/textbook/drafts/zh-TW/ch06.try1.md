# 第 6 章：LLM 代理

## 本章學習目標
1. 理解結構化提示詞工程（Structured Prompt Engineering）如何透過 `SYSTEM_PROMPT` 建立严格的輸出契約，以短碼格式（Short-code Format）約束大型語言模型（LLM）的決策邊界。
2. 掌握容錯 JSON 解析機制，特別是 `parse_plan` 函式如何利用 `raw_decode` 從夾帶雜訊、Markdown 圍欄或冗長文字中精確提取第一個合法 JSON 物件。
3. 認識多後端 Completer 架構的設計邏輯，包括雲端 API 後端 `OpenAIChatCompleter`、離線演示後端 `DemoCompleter` 以及外部命令後端的抽象介面。
4. 分析延遲抑制策略，理解關閉 `enable_thinking` 參數如何縮短推論時間，避免長鏈推理造成的超時問題。
5. 深入探討異常隔離與斷路器（Circuit Breaker）模式，了解 `CircuitBreakerCompleter` 如何防範連續 API 故障，以及 `ConfigError` 如何快速暴露設定缺陷。

## 6.1 系統提示詞工程：SYSTEM_PROMPT 規範嚴格輸出契約與短碼格式

在分層 AI 決策架構中，LLM 代理層（Agent Layer）的核心職責是將非結構化的遊戲狀態轉換為結構化的決策指令。由於 LLM 本質上是機率性文字生成模型，其輸出具有不確定性，因此必須透過嚴格的提示詞工程（Prompt Engineering）建立「輸出契約」（Output Contract）。在 `llm_agent.py` 中，`SYSTEM_PROMPT` 變數承擔了定義此契約的關鍵角色。

`SYSTEM_PROMPT` 的設計遵循「最小必要資訊」與「明確約束」原則。首先，它明確界定代理的角色為「勢力的謀主」，並強調每位出場武將每回合至多一個行動。這種限制不僅符合遊戲引擎的結算邏輯，也降低了 LLM 產生衝突指令的機率。其次，提示詞嚴格規定行動必須取自該武將的 `legal` 清單，且參數須在合法範圍內。這確保了 LLM 不會嘗試執行引擎不支援的動作（如未解鎖的科技或非法的移動路徑）。

為了應對 LLM 常見的「長文本傾倒」（Verbose Output）問題，`SYSTEM_PROMPT` 採用了「短碼格式」（Short-code Format）的輸出規範。它要求輸出只能是一個 JSON 物件，且明確禁止輸出 JSON 以外的文字。具體而言，提示詞中包含了詳細的範例，例如：
```json
{"officer":"<officer_id>","action":"move","params":{"to":"<city_id>"},"memo":"…"}
```
這種範例驅動（Example-driven）的設計顯著提升了模型對格式的理解能力。特別值得注意的是，提示詞中明確指出 `params` 的鍵名必須與 `legal` 清單中的鍵名完全相同，且值為單一字串或數字，不可為陣列。這直接針對了實驗中發現的常見錯誤，例如將 `to` 參數傳入長度為 1 的陣列 `['wancheng']`。透過在系統層面預先規定格式，我們將格式驗證的負擔從後端解析器轉移到了前端生成過程，從源頭減少解析失敗的機率。

此外，`SYSTEM_PROMPT` 還融入了戰略引導。它告知模型比較 `frontier` 中敵城的 `troops` 與 `defense`，並參考 `cast` 中的 `siege_odds`（勝算比）。提示詞明確警告：「勝算比 = 攻方戰力 ÷ 守方戰力（不含隨機）；實戰有約 ±15% 的隨機，比值低於 1.3 的出征很可能失敗並損失大量兵力」。這種將領域知識（Domain Knowledge）直接嵌入提示詞的做法，使得 LLM 不僅是執行指令，而是能夠基於即時情報進行風險評估。這體現了分層決策中「高層策略」與「低層執行」的結合，LLM 負責高層的資源分配與風險判斷，而引擎負責低層的物理結算。

## 6.2 容錯 JSON 解析：parse_plan 與 raw_decode 從夾帶雜訊之生成文本中精確提取第一個合法 JSON 物件

儘管 `SYSTEM_PROMPT` 嚴格規定輸出格式，但在實際操作中，LLM 仍可能輸出夾帶雜訊的文字，例如 Markdown 圍欄（````json ... ````）、解釋性文字、或多餘的 JSON 物件。為了應對這種不確定性，`parse_plan` 函式設計了一套魯棒的容錯解析機制。

`parse_plan` 的核心策略是「定位第一個合法 JSON 物件並忽略其餘內容」。它首先檢查輸入文字中是否包含 Markdown 圍欄標記 ` ``` `。如果存在，解析器會跳過圍欄開頭，從第一個換行符號之後開始搜尋。接著，它使用 `json.JSONDecoder` 的 `raw_decode` 方法，從第一個 `{`（或 `[`）開始嘗試解析。

`raw_decode` 與標準的 `json.loads` 不同，它只解析輸入字串開頭的一個 JSON 值，並返回該值的結束位置。這意味著，即使 LLM 在合法的 JSON 物件之後輸出了第二個物件或補充文字（即 `Extra data` 錯誤），`raw_decode` 也能成功提取第一個完整物件，而不會拋出異常。這一特性徹底解決了實驗中觀察到的「JSON 多餘內容問題」。在第二階段評測中，有 6 次解析失敗皆因 `Extra data` 導致，而在第三階段升級 `parse_plan` 使用 `raw_decode` 後，解析失敗次數降為 0。

除了處理多餘內容，`parse_plan` 還具備「參數別名正規化」（Alias Normalization）功能。LLM 可能使用非標準的參數名稱，例如用 `target`、`destination`、`dest` 代替 `to`，或用 `troop`、`soldiers`、`army` 代替 `troops`。解析器定義了 `TO_ALIASES` 和 `TROOPS_ALIASES` 元組，並在解析過程中自動將這些別名映射回標準鍵名。此外，它還會處理數值型別轉換，例如將整數值的浮點數（如 `10.0`）轉換為整數（`10`），以及將長度為 1 的陣列自動解包為單一字串或數字。這些正規化步驟顯著提升了指令的接受率，使得即使 LLM 的輸出存在輕微偏差，系統仍能正確解讀其意圖。

`parse_plan` 還負責驗證 `orders`、`chronicle` 和 `next_cast` 欄位的結構完整性。例如，它檢查 `orders` 是否為列表，每個 order 是否為字典，且包含有效的 `officer` 和 `action` 欄位。對於 `next_cast`，它限制長度為 12 個元素，並確保每個元素為字串。這種多層次的驗證機制確保了進入引擎層的資料一定是結構正確且符合規範的，從而維護了系統的安全性與穩定性。

## 6.3 多後端 Completer 架構：OpenAIChatCompleter、離線 DemoCompleter 與外部命令後端

為了實現系統的可移植性與可測試性，LLM 代理層採用了抽象的 `Completer` 介面，定義為 `Callable[[str, str], str]`，即接收系統提示詞與使用者提示詞，回傳文字響應。這種設計允許在不同的運行環境下替換後端實現，而無需修改代理核心的邏輯。

`OpenAIChatCompleter` 是主要的雲端後端實現，它使用 Python 標準庫的 `urllib` 呼叫 OpenAI 相容的 `/chat/completions` 端點。該類接受 `base_url`、`model`、`api_key_env`、`timeout`、`temperature` 和 `max_tokens` 等參數。值得注意的是，`temperature` 預設為 0.2，這有助於降低輸出的隨機性，提高決策的一致性。`max_tokens` 預設為 900，限制了單次回應的长度，避免過長的生成導致超時或成本過高。`OpenAIChatCompleter` 還支援 `extra_body` 參數，允許傳入額外的請求體欄位，例如用於本機模型的 `chat_template_kwargs`。在處理 API 錯誤時，它會捕獲 `HTTPError` 和 `URLError`，並將其轉換為 `RuntimeError`，同時對錯誤訊息中的 API 金鑰進行遮蔽（Redaction），防止敏感資訊洩漏。

`DemoCompleter` 是一個離線演示後端，用於在沒有網路連線或 API 金鑰的環境下進行測試與演示。它不依賴外部 LLM，而是根據輸入的遊戲狀態，使用規則邏輯生成決策。例如，它會遍歷 `cast` 中的武將，選擇第一個非 `rest` 的合法行動，並生成相應的 `orders`。`DemoCompleter` 的實現依賴於 `_parse_legal_str` 函式，該函式解析 `legal` 清單中的字串，提取行動名稱與參數。這種後端對於單元測試與快速驗證系統流程非常有用，因為它的行為是確定性的，且執行速度極快。

此外，`backends.py` 還提供了 `CommandCompleter`，用於執行外部命令列程式（CLI）來生成補全。這允許使用者整合自訂的本地模型或腳本。`CommandCompleter` 透過 `subprocess.run` 執行指定的 `argv`，並支援 `{prompt_file}` 佔位符，以便將提示詞寫入臨時檔案並傳給外部程式。這種靈活的後端架構使得系統能夠適應多種不同的 LLM 部署方式，從雲端 API 到本地 GPU 集群，再到自訂腳本，均能無縫接入。

## 6.4 思考標記與延遲抑制：關閉 enable_thinking 縮短推論時間，杜絕長鏈推理超時

在大型語言模型的推理過程中，「思考」（Thinking）或「長鏈推理」（Chain-of-Thought）雖然能提升複雜問題的解決能力，但也會顯著增加延遲與計算成本。對於實時或準實時的遊戲決策場景，過長的推論時間可能導致回合超時，影響遊戲體驗與評測效率。

為了解決這個問題，系統在呼叫本機 Qwen 大規模實驗時，明確關閉了 `enable_thinking` 參數。具體而言，透過 `OpenAIChatCompleter` 的 `extra_body` 參數傳入 `{"chat_template_kwargs":{"enable_thinking":false}}`。這使得模型直接輸出最終決策，而省略了中間的推理步驟。實驗結果顯示，關閉 `enable_thinking` 後，每組實驗僅出現 0–4 次逾時錯誤，遠低於啟用思考模式時可能產生的大量超時。

延遲抑制不僅僅是關閉思考模式，還包括對 `max_tokens` 的嚴格限制。預設的 `max_tokens` 為 900，這確保了即使模型嘗試生成冗長內容，也會在達到上限時被截斷。結合 `temperature` 的低設定（0.2），模型傾向於生成簡潔、直接的 JSON 輸出，進一步縮短了生成時間。這種「延遲抑制」策略是平衡決策品質與響應速度的關鍵。雖然關閉思考模式可能略微降低模型在極複雜戰略推理上的深度，但在本系統的遊戲情境中，決策主要依賴於即時狀態資訊（如兵力、金幣、勝算比）的簡單比較，而非長鏈邏輯推導。因此，關閉思考模式帶來的延遲優勢遠大於其潛在的推理深度損失。

此外，`CommandCompleter` 與 `OpenAIChatCompleter` 均支援 `timeout` 參數，預設分別為 180 秒與 120 秒。這為網路延遲或模型計算慢的情況提供了安全網。如果超過超時時間，系統會拋出異常，觸發重試或斷路器機制，從而避免單一請求阻塞整個遊戲迴圈。

## 6.5 異常隔離與斷路器：CircuitBreakerCompleter 防範連續 API 故障，ConfigError 快速暴露設定缺陷

在依賴外部 API 的系統中，網路不穩定、服務端錯誤或配額耗盡是常見問題。如果代理層在每次決策時都直接呼叫 API，連續的故障將導致系統反覆重試，浪費資源並延長遊戲時間。為此，系統實現了斷路器模式（Circuit Breaker Pattern），由 `CircuitBreakerCompleter` 類負責執行。

`CircuitBreakerCompleter` 包裝了一個內部的 `Completer` 實例，並追蹤連續錯誤的數量。它初始化時接受 `max_consecutive_errors` 參數，預設值為 3。當內部後端拋出異常時，`consecutive_errors` 計數器遞增；當成功返回結果時，計數器重置為 0。如果 `consecutive_errors` 達到或超過 `max_consecutive_errors`，斷路器狀態設為 `is_open = True`。在此狀態下，後續的呼叫將直接拋出 `BackendUnavailable` 異常，而不會嘗試呼叫內部後端。這有效地「熔斷」了對不可用服務的請求，防止無謂的資源消耗。

`CircuitBreakerCompleter` 對異常類型進行了區分。對於 `ConfigError`，它會立即觸發斷路器開啟，因為配置錯誤（如無效的 API 金鑰）通常不會自行恢復，繼續重試沒有意義。對於其他異常（如網路錯誤），它則根據連續錯誤次數決定是否開啟斷路器。這種設計確保了系統在面對暫時性故障時仍能嘗試恢復，而在面對永久性錯誤時能快速失敗（Fail-fast）。

`ConfigError` 是專門用於表示後端配置缺陷的異常類。在 `OpenAIChatCompleter` 中，如果環境變數中的 API 金鑰包含非 ASCII 字元或空白字元（例如貼上了佔位文字或多了換行），系統會拋出 `ConfigError`，並提供清晰的錯誤訊息，提示使用者檢查環境變數。這種快速暴露設定缺陷的機制，避免了在運行時因配置錯誤而產生的模糊故障，提升了系統的除錯效率。

在評測流程中，斷路器與呼叫預算（Call Budget）共同作用，保護雲端資源。`--max-calls` 參數設定全局累計呼叫上限，防止因無限重試或回合溢出造成 API 額度超支。當預算耗盡或斷路器開啟時，系統將優雅終止剩餘種子並輸出部分統計，確保評測結果的完整性與可重現性。

## 本章重點
1. `SYSTEM_PROMPT` 透過明確的輸出契約與短碼格式範例，約束 LLM 生成結構化的 JSON 決策，並融入戰略引導資訊（如勝算比）以提升決策品質。
2. `parse_plan` 函式利用 `json.JSONDecoder.raw_decode` 從夾帶雜訊的文字中提取第一個合法 JSON 物件，解決了 `Extra data` 解析失敗問題，並具備參數別名正規化與型別轉換功能。
3. 多後端 Completer 架構提供了 `OpenAIChatCompleter`（雲端）、`DemoCompleter`（離線規則）與 `CommandCompleter`（外部命令）三種實現，確保系統在不同環境下的可移植性與可測試性。
4. 關閉 `enable_thinking` 並限制 `max_tokens` 與 `timeout`，有效抑制了 LLM 的推論延遲，避免了長鏈推理造成的超時問題，適合實時遊戲決策場景。
5. `CircuitBreakerCompleter` 實現了斷路器模式，在連續 API 故障達到閾值時熔斷連線，防止資源浪費；`ConfigError` 則用於快速暴露設定缺陷，確保系統在配置錯誤時能立即失敗並提示使用者。

## 習題
1. 假設 LLM 輸出了以下文字：`"好的，這是決策：\n```json\n{\"orders\": [...]}\n```\n希望對你有幫助。"`，請說明 `parse_plan` 如何處理此輸入，並指出 `raw_decode` 在其中的具體作用。
2. 若 `SYSTEM_PROMPT` 中未明確禁止 `params` 為陣列，LLM 可能輸出 `{"to": ["city_a"]}`。請描述 `parse_plan` 中的正規化邏輯如何處理此情況，並計算此操作對 `stats["normalized_params"]` 計數器的影響。
3. 在 `CircuitBreakerCompleter` 中，若 `max_consecutive_errors` 設為 3，且前兩次呼叫成功，第三次呼叫拋出 `RuntimeError`，第四次呼叫拋出 `ConfigError`，第五次呼叫會發生什麼？請解釋斷路器狀態的變化。
4. 比較 `OpenAIChatCompleter` 與 `DemoCompleter` 在處理 `extra_body` 參數上的差異，並說明為何 `DemoCompleter` 不需要此參數。
5. 實驗中發現，加入 `siege_odds` 偵察資訊後，LLM 的攻城嘗試從 35 次降為 0 次。請結合 `SYSTEM_PROMPT` 中的戰略引導內容，分析此現象的原因，並討論這是否代表 LLM 學會了「正確的攻擊」策略。
