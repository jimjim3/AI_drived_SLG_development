# LLM 勢力決策評測說明與基準紀錄

## 1. 評測目的
本評測旨在評估大型語言模型（LLM）驅動之勢力決策代理在三國 SLG 環境下的策略表現。由於各勢力初始條件（地理位置、將領素質、初始兵力與城池數量）具高度結構性差異（如曹操勢力先天資源優渥），直接比較跨勢力勝率並不具備科學意義。因此評測採取**同座位同種子成對比較**（Paired Comparison）：在相同隨機種子下，分別由 LLM 代理與規則 AI（Rule-based baseline）掌管同一席位（預設為 `faction_2` 劉備勢力），其餘勢力維持相同之規則代理，以精確量化 LLM 相較於規則基準線的增益或劣勢。

## 2. 評測方法與指令
評測由模組 `slg.sim.evaluate` 執行成對模擬，並自動輸出 Markdown 與 JSON 報告。

```bash
# 使用環境變數傳遞金鑰，並指定金鑰環境變數名稱（金鑰勿寫入指令或程式碼）
PYTHONPATH=src python3 -m slg.sim.evaluate \
  --seat faction_2 \
  --seeds 0-5 \
  --turns 20 \
  --max-calls 130 \
  --model gemini-3.5-flash-lite \
  --api-key-env GEMINI_API_KEY \
  --out docs/evals/rep.md
```

## 3. 預算保護與斷路器
- **呼叫預算（Call Budget）**：透過 `--max-calls` 設定全局累計呼叫上限（如 130 次），防止因無限重試或回合溢出造成 API 額度超支。預算耗盡時系統將優雅終止剩餘種子並輸出部分統計。
- **斷路器機制（Circuit Breaker）**：由 `--max-consecutive-errors` 控制（預設 3 次）。若後端連續發生連線異常或 HTTP 錯誤達到上限，斷路器自動熔斷並即時中止評測流程，避免無謂消耗配額。

2. **單一模型**：僅代表特定輕量級模型（gemini-3.5-flash-lite）之指令遵循表現，不同參數量模型對參數格式遵循度差異可能極大。

### 7.2 重要發現與診斷
1. **參數格式錯誤已由提示詞示範解決**：提示詞加入明確動作用法示範（如 `move: {"to": "<city_id>"}`）及禁止陣列的規定後，前次最為嚴重的遺漏 `to`（44 次）與傳入長度 1 陣列（10 次）問題徹底消除，指令接受率從 84.1% 大幅躍升至 94.3%。
2. **出征勝算判斷是 LLM 的主要弱點**：模型在視圖中雖然看得到敵城 `troops` 與 `defense`，但無法心算複雜攻防換算公式，35 次攻城 0 次成功（全被擊退），白白折損大量部隊，導致最終兵力大幅落後規則 AI 約 3800（-38.4%），為制約戰略表現的核心瓶頸。
3. **JSON 多餘內容問題**：評測中出現 6 次解析失敗，錯誤類型皆為 `Extra data`（模型輸出完整 JSON 物件後，在尾端多寫了第二個物件或補充文字），導致 `json.loads` 拒絕並引發重試，消耗多餘 API 額度。

## 8. 第三階段評測：出征勝算偵察（2026-10-11 已評測）

> [!NOTE]
> 與前兩階段相同條件：`gemini-3.5-flash-lite`、faction_2 席位、種子 0–5、每局 20 回合。原始報告見
> `docs/evals/2026-10-11_gemini-3.5-flash-lite_seat-faction_2_after-siege-odds.{md,json}`。

### 8.1 本階段改進要點
1. **解析器取第一個完整 JSON 物件**：升級 `llm_agent.parse_plan`，改用 `json.JSONDecoder().raw_decode` 從第一個 `{` 開始解析，自動忽略其後的第二個物件或多餘文字，徹底根治 `Extra data` 解析失敗問題。
2. **共用出征勝算比估計**：於 `engine/resolution.py` 抽出 `_siege_strengths` 共用算式，新增公開純函式 `estimate_siege_ratio`（攻守戰力比，隨機項恆取 1.0），確保估計與實戰使用同一公式。
3. **視圖加入勝算偵察（`siege_odds`）**：於 `engine/view.py` 的 `FactionView.cast` 中，凡具備 `siege` 合法行動的武將均新增 `siege_odds`（`{目標城id: 勝算比}`，四捨五入至小數 2 位，`inf` 代以 99.0），提供即時偵察情報。
4. **系統提示詞引導戰略**：更新 `SYSTEM_PROMPT`，明確告知勝算比意義、實戰約 ±15% 隨機波動，並警告比值低於 1.3 的出征極易潰退，引導模型避開盲目進攻。

### 8.3 結論與限制
- ② 階段 35 次攻城全數被擊退，是兵力落後的主因；③ 階段 LLM 看到勝算比後**完全不再出征**，兵力與城數回到與規則 AI 基準相當（+472 兵、0 城差）。
- 注意：③ 的改善是「避免了錯誤的攻擊」，**不是學會了正確的攻擊**。規則 AI 基準本身在這 20 回合內也幾乎不出征，因此本評測尚未檢驗 LLM 在有利局面下是否懂得進攻。
- 剩餘被拒指令（約 6%）主要是 `troops` 超出範圍與同城金幣被先行指令耗盡造成的 `develop_*` 不合法，屬資源排序問題。

- 建議的下一步：加長局數（≥40 回合）、加入較強模型對照（如 `gemini-3.5-flash`）、設計「LLM 應該進攻」的情境（例如兵力優勢劇本）以檢驗進攻判斷。

(a) 重新調整冷落／忠誠機制（縮短門檻或加大懲罰）並以長局驗證；(b) 在視圖加入「各城可用金幣預算」以降低資源爭用造成的拒絕；(c) 在提示詞或視圖標示低勝算出征的風險並記錄出征時的勝算比，以診斷冒進；(d) 平衡座位優勢後重做自我對弈；(e) 增加種子數並加上信賴區間。

## 10. 忠誠／冷落機制重調（2026-10-11）

**問題**：第 9 節的真實 LLM 玩法（每回合點名約 4.5/14 位武將）在 40 回合內 0 出奔、0 抗旨，平均忠誠僅由約 89 緩降至約 79——冷落門檻對這種玩法太寬，機制沒有「牙齒」。

## 13. 三家 Qwen 自我對弈，以及「對手為什麼不出兵」（2026-10-18）

**設定**：`scripts/selfplay.py`，三家都由 Colab Qwen3.8-27B（Q4_K_M，`reasoning_effort:none`）操控，預設情境、20 回合；腳本區分「LLM 下令的出征」與「規則 AI 代管武將的出征」。原始結果見 `docs/evals/qwen/q9*.json`、`q10*.json`、`q11*.json`。

| 實驗 | 設定 | 種子 | LLM 出征令 | 代管出征（成功） | 被拒指令 | 勝者 |
|---|---|---|---|---|---|---|
| Q9 | 出征判定開 | 0、1 | **0、0** | 0、4（0） | 12.1%、10.7% | faction_3、faction_3 |
| Q10 | 判定關 | 0、1 | 2（0 成功）、0 | 3、4（1） | 11.7%、8.7% | faction_3、faction_3 |
| Q11 | 判定開＋**進取個性** | 0、1 | **0、0** | 0、4（0） | 14.3%、15.5% | faction_3、faction_1 |

### 發現
1. **加進取個性並沒有讓 LLM 出兵**（Q11 的 LLM 出征令仍為 0）。判定開時 LLM 完全不出征（Q9），判定關時偶爾冒進且全數失敗（Q10：2 次、0 成功）。
2. **根因不是模型，是戰鬥平衡**：用規則 AI 對局量測每個勢力每回合「手上最好的出征目標」的偵察勝算比（`scripts/attack_opportunities.py`，4 個種子 × 20 回合）：

   | 情境 | 勢力 | 中位數 | 最大值 | 勝算比 ≥1.3 的回合 | ≥1.0 的回合 |
   |---|---|---|---|---|---|
   | 預設 | 三家 | 0.34–0.39 | **0.54–0.70** | **0/80（三家皆然）** | 0/80 |
   | 進攻局 | faction_2（占優） | 0.59 | 2.67 | 7/80 | 8/80 |
   | 進攻局 | faction_1／faction_3 | 0.37 | 0.77／1.07 | 0 | 0／4 |

   預設情境 240 個「勢力×回合」裡**從來沒有出現過勝算比 ≥1.0 的目標**，所以 Qwen 不出兵是理性的。公式上（`engine/resolution.py::_siege_strengths`）：攻方戰力＝出征兵力×(0.5＋(武＋統)/200)，頂級武將約 ×1.4；守方戰力＝守軍×(1＋城防/200)×(0.5＋最強守將/100)，典型約 ×2.1–2.3；且出征兵力只能從**單一城池**抽（扣最低留守），無法集結多城兵力。同樣兵力下守方強約 1.5–1.7 倍，攻方得在一座城裡擁有約兩倍守軍才有利。
3. **因此「對手被動」是遊戲設計問題**，換模型、換提示都治不了：三方對稱成長時沒有人有理由進攻，勝負只看經濟。
4. **座位優勢仍在**：孫權（faction_3）在 Q9、Q10 的 4 局全勝；Q11 的 2 局勝者各一（faction_3、faction_1），不足以說已改善。
5. 被拒指令約 9–16%，仍以同城金幣被先行指令用完為主。

### 建議（尚未實作；會改變所有既有評測的基準，需要先決定）
可用 `scripts/attack_opportunities.py` 在調整前後量測「出現勝算比 ≥1.3 的回合比例」作為驗收：
- 降低守方優勢：例如把城防倍率 `defense/200` 改為 `defense/400`，或降低守將權重；
- 允許集結兵力：增加城間運兵，或讓出征可抽調鄰近己方城的兵力；
- 讓守方消耗：攻城失敗仍造成守方損耗，讓連續進攻有意義；
- 目標不是讓攻擊必勝，而是讓「有條件時進攻」成為合理選項（例如 20 回合內 20–40% 的回合存在 ≥1.3 的機會）。

### 限制
Q9–Q11 各只有 2 個種子；進取個性只測了一種措辭；勝算比量測用的是規則 AI 的對局軌跡，LLM 的對局軌跡可能略有不同。

- 預設規則仍為 `v2`；`softer_pool2` 在孫權問題解決前不建議設為預設。
- 限制：單一模型（Nemotron Super），每組 10 局。

#### 觀測與成因分析
1. **行軍糧耗的門檻斷崖效應**：
   - 當 `march_food_rate >= 0.75` 時，建業—襄陽（628 km）出征 1000 兵需消耗 471～628 糧。建業起始僅 900 糧，扣除徵兵與日常開銷後，常常無法滿足出發門檻（`validate_decision` 直接拒絕，規則 AI 略過）。在 `r=1.0` 下孫權 40 局出征數皆為 0（完全癱瘓），曹操 40/40 全勝；在 `r=0.75` 下出征次數亦自 31 次腰斬至 15 次。
   - 當降至 `march_food_rate <= 0.5`（糧耗減半至 314 糧以內）時，糧耗不再成為不可逾越的門檻，孫權恢復主動進攻（出征 31～43 次），各局城池易手正常。
2. **城池上限階級的影響**：
   - **Koei 原版階級**：會稽上限較小（1100 兵），曹操保有中原大城總體量優勢（許昌 2000、襄陽 2000、陳留 1600 合計 5600 vs 孫權 4700）。曹操勝率約 67.5%～70%，孫權 25%，劉備 5%～7.5%。三方皆有勝局，孫權達到「偏安且活躍、但非絕對優勢」的設計預期。
   - **平坦化 Flat 階級**：縮小城池上限差距（會稽提升至 1750、建業 2200），孫權後方安全且體量充足，局勢反轉為孫權占優（勝率 60%、曹操 40%），但劉備在兩強夾擊下勝率降至 0%。
3. **遠路戰力折損（`far_march_factor=0.75`）造成雙重懲罰**：
   - 在已啟用行軍糧的情況下若再疊加 `far_march_factor=0.75`，孫權攻襄陽與劉備漢中出兵同時承受「高糧耗」與「戰力 ×0.75」雙重折損，導致防守方（占據襄陽/中原的曹操）過度得益，曹操勝率再度飆高至 85%～87.5%。因此純粹用「行軍糧」作為距離調節機制優於兩者疊加。

#### 推薦規則集
1. **主選：`softer_pool2_econ3`**（新增至 `src/slg/engine/combat.py`）：
   - 參數：Koei 規模階級（`city_caps=True, cap_tiers=True`）、行軍糧率減半至 **0.5**（`march_food_rate=0.5`）、不疊加遠路戰力折損（`far_march_factor=1.0`）。
   - 表現：曹 28 勝 (70%)、孫 10 勝 (25%)、劉 2 勝 (5%)。孫權出征 31 次，保持進攻活力，且不再獨霸；三國皆有勝機。
