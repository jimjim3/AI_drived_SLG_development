# LLM 勢力決策評測說明與基準紀錄

## 1. 評測目的
本評測旨在評估大型語言模型（LLM）驅動之勢力決策代理在三國 SLG 環境下的策略表現。由於各勢力初始條件（地理位置、將領素質、初始兵力與城池數量）具高度結構性差異（如曹操勢力先天資源優渥），直接比較跨勢力勝率並不具備科學意義。因此評測採取**同座位同種子成對比較**（Paired Comparison）：在相同隨機種子下，分別由 LLM 代理與規則 AI（Rule-based baseline）掌管同一席位（預設為 `faction_2` 劉備勢力），其餘勢力維持相同之規則代理，以精確量化 LLM 相較於規則基準線的增益或劣勢。

## 2. 評測方法與指令
評測由模組 `slg.sim.evaluate` 執行成對模擬，並自動輸出 Markdown 與 JSON 報告。

```bash
# 使用環境變數傳遞金鑰，並指定金鑰環境變數名稱（金鑰勿寫入指令或程式碼）
PYTHONPATH=src python3 -m slg.sim.evaluate \
  --seat faction_2 \
  --seeds 0-5 \
  --turns 20 \
  --max-calls 130 \
  --model gemini-3.5-flash-lite \
  --api-key-env GEMINI_API_KEY \
  --out docs/evals/rep.md
```

## 3. 預算保護與斷路器
- **呼叫預算（Call Budget）**：透過 `--max-calls` 設定全局累計呼叫上限（如 130 次），防止因無限重試或回合溢出造成 API 額度超支。預算耗盡時系統將優雅終止剩餘種子並輸出部分統計。
- **斷路器機制（Circuit Breaker）**：由 `--max-consecutive-errors` 控制（預設 3 次）。若後端連續發生連線異常或 HTTP 錯誤達到上限，斷路器自動熔斷並即時中止評測流程，避免無謂消耗配額。

## 5. 診斷發現
1. **參數格式錯誤占被拒指令 91%**：在 70 次被拒指令中，高達 64 次（91.4%）起因於參數格式錯誤（44 次遺漏 `to` 參數、10 次將 `to` 傳入長度為 1 之陣列如 `['wancheng']`、10 次出征兵力超出合法範圍），顯示提示詞範例缺乏與解析器過於嚴格為主要瓶頸。
2. **攻城激進致兵力大損**：LLM 共主動攻城 42 次（基準線為 0 次），但多數出征未形成兵力壓制而受挫，造成實驗組最終兵力大幅落後基準線（平均兵力差 -3830.3）。
3. **將領忠誠與委任運作良好**：出奔數為 0、抗旨數為 0，冷落機制與委任代行未引發將領流失。

## 6. 限制說明
1. **樣本規模**：初次評測僅包含 6 個隨機種子，單局偶發事件（如曹操勢力初期併吞）對勝率影響顯著，不具統計顯著性；正式結論建議採用 20 個以上種子。
2. **單一模型**：僅代表特定輕量級模型（gemini-3.5-flash-lite）之指令遵循表現，不同參數量模型對參數格式遵循度差異可能極大。

### 7.2 重要發現與診斷
1. **參數格式錯誤已由提示詞示範解決**：提示詞加入明確動作用法示範（如 `move: {"to": "<city_id>"}`）及禁止陣列的規定後，前次最為嚴重的遺漏 `to`（44 次）與傳入長度 1 陣列（10 次）問題徹底消除，指令接受率從 84.1% 大幅躍升至 94.3%。
2. **出征勝算判斷是 LLM 的主要弱點**：模型在視圖中雖然看得到敵城 `troops` 與 `defense`，但無法心算複雜攻防換算公式，35 次攻城 0 次成功（全被擊退），白白折損大量部隊，導致最終兵力大幅落後規則 AI 約 3800（-38.4%），為制約戰略表現的核心瓶頸。
3. **JSON 多餘內容問題**：評測中出現 6 次解析失敗，錯誤類型皆為 `Extra data`（模型輸出完整 JSON 物件後，在尾端多寫了第二個物件或補充文字），導致 `json.loads` 拒絕並引發重試，消耗多餘 API 額度。

## 8. 第三階段評測：出征勝算偵察（2026-10-11 已評測）

> [!NOTE]
> 與前兩階段相同條件：`gemini-3.5-flash-lite`、faction_2 席位、種子 0–5、每局 20 回合。原始報告見
> `docs/evals/2026-10-11_gemini-3.5-flash-lite_seat-faction_2_after-siege-odds.{md,json}`。

### 8.1 本階段改進要點
1. **解析器取第一個完整 JSON 物件**：升級 `llm_agent.parse_plan`，改用 `json.JSONDecoder().raw_decode` 從第一個 `{` 開始解析，自動忽略其後的第二個物件或多餘文字，徹底根治 `Extra data` 解析失敗問題。
2. **共用出征勝算比估計**：於 `engine/resolution.py` 抽出 `_siege_strengths` 共用算式，新增公開純函式 `estimate_siege_ratio`（攻守戰力比，隨機項恆取 1.0），確保估計與實戰使用同一公式。
3. **視圖加入勝算偵察（`siege_odds`）**：於 `engine/view.py` 的 `FactionView.cast` 中，凡具備 `siege` 合法行動的武將均新增 `siege_odds`（`{目標城id: 勝算比}`，四捨五入至小數 2 位，`inf` 代以 99.0），提供即時偵察情報。
4. **系統提示詞引導戰略**：更新 `SYSTEM_PROMPT`，明確告知勝算比意義、實戰約 ±15% 隨機波動，並警告比值低於 1.3 的出征極易潰退，引導模型避開盲目進攻。

### 8.3 結論與限制
- ② 階段 35 次攻城全數被擊退，是兵力落後的主因；③ 階段 LLM 看到勝算比後**完全不再出征**，兵力與城數回到與規則 AI 基準相當（+472 兵、0 城差）。
- 注意：③ 的改善是「避免了錯誤的攻擊」，**不是學會了正確的攻擊**。規則 AI 基準本身在這 20 回合內也幾乎不出征，因此本評測尚未檢驗 LLM 在有利局面下是否懂得進攻。
- 剩餘被拒指令（約 6%）主要是 `troops` 超出範圍與同城金幣被先行指令耗盡造成的 `develop_*` 不合法，屬資源排序問題。
- 樣本僅 6 個種子且單一模型，勝率差異（1/6 對 1/6 或 0/6）不具統計顯著性；兵力與城數的方向性結論也需要更多種子與更長局數驗證。
- 建議的下一步：加長局數（≥40 回合）、加入較強模型對照（如 `gemini-3.5-flash`）、設計「LLM 應該進攻」的情境（例如兵力優勢劇本）以檢驗進攻判斷。
