# 設計文件：分層 AI 決策的回合制 SLG

## 0. 核心原則

1. **引擎是唯一的真理來源。** AI 只能從引擎產生的「合法行動清單」中挑選；引擎在執行前再驗證一次。
   AI 永遠不直接改遊戲狀態。
2. **AI 是可替換的「決策插件」。** 同一個介面可以接 LLM、規則 AI、隨機 AI、甚至人類玩家。
   這讓你能做 A/B 對照，也讓 LLM 掛掉時可自動退回規則 AI。
3. **每一層只看得到它「應該知道」的事。** Prompt 就是角色的感知：戰爭迷霧、情報誤差、
   部下謊報，都在組 Prompt 時由引擎決定。

## 1. 分層：建議用三層，而不是兩層

KOEI 三國志 II～IX 的實際運作單位是「城」：君主下令，太守（或委任）執行，武將是被指派的人力。
建議把分層定為：

| 層級 | 決策頻率 | 看到的資訊 | 輸出 |
|---|---|---|---|
| 君主（Ruler） | 每回合 1 次（或每季） | 全勢力摘要、外交、已知敵情 | **戰略指令**：各城的角色（前線/後勤/開發）、外交動作、主攻目標 |
| 太守（Governor） | 每回合每城 1 次 | 本城詳細狀態、君主指令、城內武將名冊 | **城內配置**：把城內武將分派到各工作 |
| 武將（Officer） | **事件驅動**，不是每回合 | 自身狀態、任務、性格、記憶 | 只在有裁量空間時才問：戰場戰術、被策反時、奉命出使時的談判 |

為什麼要加「太守」這層：它是天然的**批次單位**。一次呼叫決定整座城 5～10 位武將的工作，
比每位武將各呼叫一次便宜一個數量級，而且更符合原作手感。

### 意圖下傳（Intent Passing）要結構化

君主的指令不要只傳自然語言，要傳 **結構化意圖 + 一句話說明**：

```json
{
  "city": "xuchang",
  "role": "frontline_defense",
  "priority": ["train", "recruit", "fortify"],
  "latitude": 0.3,
  "note": "兩回合後將發兵洛陽，許昌務必守住"
}
```

`latitude`（裁量權）決定下層能偏離多少——這把「服從」變成一個可調、可觀察的數值，而不是 Prompt 裡的祈禱。

## 2. 行動空間：引擎產生、AI 挑選

每次呼叫時，引擎動態產生當下合法的行動（含參數範圍），以 tool/function calling 或 JSON Schema 交給模型：

```json
{
  "actor": "zhuge_liang",
  "legal_actions": [
    {"id": "develop_agri", "cost": {"gold": 50}},
    {"id": "recruit", "params": {"troops": {"min": 100, "max": 1200, "step": 100}}},
    {"id": "move", "params": {"to": ["luoyang", "wan"]}},
    {"id": "rest"}
  ]
}
```

模型回傳：

```json
{"action": "recruit", "params": {"troops": 800}, "memo": "洛陽空虛，不可不防"}
```

- `memo` 就是「奏摺」：≤20 字，成本極低，沉浸感極高。
- 解析失敗 / 超時 / 選到非法行動 → 重試一次 → 仍失敗就退回規則 AI，並記錄在日誌。
- 盡量使用 constrained decoding（結構化輸出），讓非法輸出在生成階段就不可能出現。

## 3. Token 預算：要先算，不要假設

「Token 不會太大」要看怎麼切。以 20 個勢力、每勢力平均 5 城估算：

| 設計 | 每回合呼叫數 | 每次約 tokens（入+出） | 每回合 tokens |
|---|---|---|---|
| 每位武將每回合都問（~400 人） | ~420 | 1,500 | **~630k** |
| 君主 + 太守批次（本文建議） | 20 + 100 = 120 | 2,000 | **~240k** |
| 再加：只有玩家可見 / 前線城用 LLM，其餘規則 AI | ~40 | 2,000 | **~80k** |

一局 300 回合，差距是 1.9 億 vs 2,400 萬 tokens。省 Token 的手段：

- **Prompt caching**：規則說明、角色設定放在固定前綴，每回合只變動狀態區塊。
- **事件驅動**：沒有新情況的城沿用上回合方針（「維持現狀」本身就是一個零成本行動）。
- **模型分級**：君主用強模型；太守/武將用本地小模型（Ollama / llama.cpp 等）。
- **同回合並行**：各勢力「同時決策、依序結算」，延遲 = 最慢的那一次呼叫，而不是總和。

## 3.5 替代方案：勢力敘事模式（每勢力每回合一次呼叫）

每個勢力每回合只呼叫一次 LLM，以「史官／說書人」的角度寫出這一回合。重點是**一次輸出兩樣東西**：

```json
{
  "orders": [
    "xuchang: 荀彧 develop_agri; 夏侯惇 recruit 800",
    "chenliu: 曹仁 move -> xuchang"
  ],
  "chronicle": "許昌方面，荀彧勸課農桑；夏侯惇以洛陽空虛為憂，募兵八百。曹仁奉命自陳留移屯許昌……"
}
```

規則：

1. **指令用精簡的短碼（DSL），不要讓引擎去解析散文。** 由引擎逐條驗證，非法指令直接丟棄並記錄。
2. **沒被點名的武將由引擎「委任」自動分派。** 100 字只寫得下幾個重點人物；LLM 決定重點，其他人交給規則 AI。
3. **正式史書要在結算之後才寫。** 事前寫的只是「意圖」；戰果要等引擎結算後才寫，才不會出現「文中攻下洛陽、實際上敗退」的矛盾。
   可以在下一回合的同一次呼叫中順便寫上一回合的正式紀錄，不必多呼叫一次。
4. **真正的成本在輸入。** 輸出 100 字很便宜，但輸入要附上整個勢力的狀態；大勢力後期可能有 200 位武將。
   武將清單要壓縮成每人一行（如 `荀彧 政98 忠95 許昌 空閒`），並把固定內容放進可快取的前綴。

估算：20 勢力 × 每次約 3k tokens，每回合約 **6 萬 tokens**，約是三層架構的四分之一。

### 3.6 出場名單：讓輸入量不隨勢力規模成長

在每回合的輸出中多加一欄 `next_cast`，由 LLM 指定**下一回合要詳細看**的武將。下一回合的輸入只展開這些人。

```json
{"orders": [...], "chronicle": "...", "next_cast": ["荀彧", "夏侯惇", "曹仁"]}
```

下一回合的輸入由四個部分組成：

| 區塊 | 內容 | 約 tokens |
|---|---|---|
| 勢力摘要（固定大小） | 各城兵糧金、外交、已知敵情 | ~300 |
| 出場名單 | LLM 上回合指定的武將，每人一行詳細資料，上限 5～8 人 | ~200 |
| **引擎強制插入** | 本回合有事件的武將：新登用、被俘、忠誠驟降、所在城被攻 | ~0–150 |
| 其餘名冊（只列名字，依城分組） | `陳留: 李典 樂進 于禁…`，讓 LLM 可以點名其他人 | ~3／人 |

「引擎強制插入」必不可少：LLM 在上回合無法預知本回合的突發事件，如果只看自己選的名單，就會對新發生的事視而不見。

**把限制變成玩法：受冷落。** 連續多回合沒被點名的武將，忠誠度緩慢下降，並累積「懷才不遇」。
超過門檻時，引擎觸發**毛遂自薦**事件，把他強制插入名單；若仍被忽視，就可能出奔。
技術上的注意力上限，變成了「君主精力有限」的遊戲機制。

估算：每次輸入約 1k～1.5k tokens，**與勢力大小幾乎無關**；20 勢力每回合約 3 萬 tokens。

**聚光燈機制（混合模式）：** 平時用勢力敘事模式；遇到戲劇性時刻（忠誠低落被策反、單挑、臨陣倒戈、外交談判），
才替**該武將**單獨呼叫一次，以其自身視角和記憶決策。這樣可以保留「每位武將由 AI 決定」的精神，成本也不會失控。

## 4. 抗旨與叛變：交給引擎擲骰，LLM 只負責「怎麼演」

如果讓 LLM 自己決定要不要抗旨，玩家無法分辨「角色有野心」和「模型沒聽懂」。建議拆開：

1. 引擎根據 忠誠、野心、君主威望、`latitude`、局勢 計算 **偏離機率**並擲骰。
2. 擲出「服從」→ 合法行動清單裡只有符合指令的選項。
3. 擲出「偏離」→ 清單裡才會出現 `ignore_order` / `defect` / `rebel` 等選項，並在 Prompt 告知「你心生異志」。
4. LLM 的工作是**選擇怎麼偏離、並寫出合理的奏摺或檄文**。

這樣抗旨永遠是**可被系統解釋的遊戲事件**（可在日誌/UI 上顯示「忠誠 42、野心 88 → 判定偏離」），
不會被當成 bug；同時保留 LLM 帶來的意外感。

延伸玩法：低忠誠武將的奏摺可以**說謊**（引擎知道真相，玩家只看到奏摺）——這是傳統 AI 很難做出的體驗。

## 5. 記憶與性格

- 每位武將一段 ≤100 字的「人物記憶」，由引擎在重大事件後以小模型摘要更新（被救、被貶、親人戰死）。
- 性格用少量數值 + 一句話標籤（例：「謹慎，重信義，厭惡曹操」），不要塞整篇列傳。

## 6. 可重現性與評測（開源專案的生命線）

- 所有 Prompt / 回應 / 亂數種子寫入回合日誌，可**完整重播**。
- Headless 模式：無畫面跑整局，用來比較「LLM vs 規則 AI」勝率、平均存活回合、每回合 tokens。
- 性格一致性指標：同一武將在相似情境下的選擇分布是否符合其性格標籤。
- 這些數據本身就是很好的 README 展示材料，也方便其他人貢獻新模型/新 Prompt 來比。

## 7. 建議的技術路線

```
game-core (Python, 無畫面, 純規則+狀態)   ← 先做這個
   ├─ agents/  rule_based.py  llm_agent.py  human.py
   ├─ sim/     headless 對戰、評測腳本
   └─ api/     JSON/WebSocket 介面
frontend (之後再選：Web / Godot)          ← 只負責顯示與玩家輸入
```

把遊戲核心做成 headless Python，前端只透過 API 溝通，理由：

- LLM 生態系在 Python 最完整；
- headless 才能大量自動對戰評測；
- 前端可以後換，不被引擎綁死（Godot 的 Python 支援屬社群專案，不建議把核心邏輯押在上面）。

## 8. 里程碑

1. **M0**：5 城、3 勢力、~20 武將的迷你劇本；只有 內政/徵兵/移動/攻城；規則 AI 可跑完整局。
2. **M1**：君主層接 LLM；日誌與重播。
3. **M2**：太守層批次決策 + 奏摺。
4. **M3**：忠誠/偏離機制、人物記憶。
5. **M4**：評測報告（LLM vs 規則 AI、tokens/回合）。
6. **M5**：前端。
